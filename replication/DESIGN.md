# replication/ — Navigation Guide

Real-time, peer-to-peer replication of table data across cluster nodes via persistent WebSocket connections. Implements eventual consistency: when a local transaction commits, the audit records are forwarded asynchronously to peers.

**Read this when:** you're touching cluster sync, debugging missed writes, JWT/cluster auth, latency-based node selection, or blob transfer between nodes.

**Integration boundary with core:** replication hooks into core's table resource layer — a `Replicator` class is installed as a `source` of the table (`table.sourcedFrom(class Replicator extends Resource {...})`). When a local cache miss occurs, the Replicator picks the lowest-latency peer and fetches. Core's audit store (`core/resources/auditStore.ts`) and node-id mapping (`core/resources/nodeIdMapping.ts`) are the two data structures replication reads.

> **Navigation convention.** Code is referenced by **symbol name** (class, function, exported const). Use your editor's go-to-symbol or `grep -n '<name>' replication/<file>` to jump. Line numbers drift; symbols don't.

## Key abstractions

### `NodeReplicationConnection` (`replicationConnection.ts`)

A persistent connection to one remote node. Owns the WebSocket lifecycle, reconnection (initial delay `INITIAL_RETRY_TIME`), latency tracking, and per-subscription state. **Inspect this when debugging connection drops or auth failures.**

### `replicateOverWS(ws, options, authorization)` (`replicationConnection.ts`)

The protocol decoder. Reads incoming binary commands — each is a top-level named const in the same file:

| Command constant                           | Value     | Meaning                                                                                           |
| ------------------------------------------ | --------- | ------------------------------------------------------------------------------------------------- |
| `SUBSCRIPTION_REQUEST`                     | 129       | Client wants to subscribe to a table                                                              |
| `RESIDENCY_LIST`                           | 130       | Negotiate which records each node holds                                                           |
| `TABLE_FIXED_STRUCTURE`                    | 132       | Schema sync                                                                                       |
| `GET_RECORD` / `GET_RECORD_RESPONSE`       | 133 / 134 | Cache-miss fetch                                                                                  |
| `OPERATION_REQUEST` / `OPERATION_RESPONSE` | 136 / 137 | Forwarded operations                                                                              |
| `NODE_NAME` / `NODE_NAME_TO_ID_MAP`        | 140 / 141 | Identity exchange                                                                                 |
| `DISCONNECT`                               | 142       | Graceful close (not used on auth failure)                                                         |
| `SEQUENCE_ID_UPDATE`                       | 143       | Audit sequence cursor                                                                             |
| `COMMITTED_UPDATE`                         | 144       | Confirm-on-commit                                                                                 |
| `DB_SCHEMA`                                | 145       | Database schema replication                                                                       |
| `BLOB_CHUNK`                               | 146       | Blob bytes                                                                                        |
| `SUBSCRIPTION_UPDATE`                      | 147       | Audit record forwarded to subscribers                                                             |
| `COPY_START`                               | 148       | Leader → follower: a bulk table copy is starting (carries `copyStartTime` + `COPY_ORDER_VERSION`) |
| `COPY_COMPLETE`                            | 149       | Leader → follower: the bulk copy finished; the follower clears its resume cursor                  |
| `RECORD_LOCK_HOMES_DIGEST`                 | 150       | Record-lock home-map digest for one database; sender-gated like the lock control entries          |

A code this build does not know falls to the switch's `default:`, which counts it on the connection and warns through a throttle shared by every socket in that worker thread, then keeps processing. It does **not** close: an unknown code means the peer is running a NEWER build, so closing would hard-loop the link — the reconnect replays the same frame. Note the consequence: the durable resume cursor still advances past a frame this build did not understand. Sender-side gating (below) is the invariant that makes that safe.

The `authorization` parameter is a **promise that may resolve asynchronously**; on rejection the socket closes without a DISCONNECT frame (relevant to JWT failure flows).

### Protocol capabilities (`protocolCapabilities.ts`)

`NODE_NAME[4]` is a msgpack map of capability keys, and `protocolCapabilities.ts` is the **only** place that interprets it. Nothing else in `replication/` may read the raw bag: a second reader is how two features end up with two different answers for "the peer didn't say."

Each socket resolves the peer's bag once per `NODE_NAME` into a frozen object with every known key present, and consults only that. The resolution is **per socket, never cached across reconnects** — `NodeReplicationConnection` outlives the socket, and a peer can be upgraded or downgraded between them.

| Key                         | Kind         | Absent ⇒          | Resolution                                                                                                                                                                                                                               |
| --------------------------- | ------------ | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `safeCopyAudit`             | strict level | `0` (unverified)  | only numeric `1` certifies a safe duplicate/no-op audit writer                                                                                                                                                                           |
| `protocolVersion`           | version      | `1`               | `min(local, peer)`; local is `LOCAL_PROTOCOL_VERSION`                                                                                                                                                                                    |
| `subscriptionSetupAck`      | level        | `0` (unsupported) | `min(local, peer)` — a level this build does not implement cannot be used                                                                                                                                                                |
| `subscriptionSetupBudgetMs` | parameter    | absent            | the peer's raw value; clamped by its consumer, never against a local level                                                                                                                                                               |
| `recordLocks`               | level        | `0` (unsupported) | exact level, never min-clamped — a peer at any other level (including a future higher one) is not a lock participant; advertised as `4` only while `replication.recordLocks` is on and the bag is sent                                   |
| `originCursors`             | level        | `0` (unsupported) | `min(local, peer)`; advertised as `1` only by a RocksDB build (per-origin logs). Gates `SUBSCRIPTION_REQUEST[4]`, an `includeNodes` update's `originCursors` and `COPY_START[3]` — see Non-obvious behavior 26                           |
| `originFloors`              | level        | `0` (unsupported) | `min(local, peer)`; advertised as `1` only by a RocksDB build. Gates the floor vector on `SEQUENCE_ID_UPDATE[2]`, its storage as `nodes[].closedFloor`, and a resume request that starts at a stored floor — see Non-obvious behavior 27 |

The kinds are not cosmetic. A **level** coerces (`Number(value)`), because the behavior being preserved is `capabilities?.subscriptionSetupAck >= 1`, a coercing comparison that a peer sending `true` or `'1'` passes today. A **parameter** does not coerce, because its predecessor was `Number.isFinite(raw) && raw > 0`, which already rejects `'300'`. A parameter is also never min-clamped: a millisecond budget is not a feature level.

An absent bag resolves to all defaults, which is exactly the pre-registry behavior, so a pre-#646 peer that sends a four-element `NODE_NAME` needs no special case anywhere.

`MINIMUM_PROTOCOL_VERSION` is **descriptive only**: it is the absent-peer default and nothing degrades or disconnects on it. Adding a version floor that closes a connection is a separate, gated decision — a floor consulted by mistake closes every link in the mesh at once, with no rollback but a redeploy.

**Which one do you add?** A capability key for an additive feature, so peers can adopt it independently. `protocolVersion` only for a change to the SHAPE of the protocol. Neither for durable state: `COPY_ORDER_VERSION` stays in the copy cursor because it describes persisted cursor content, not a peer's abilities.

**Sender-side gating discipline.** A sender must not emit a frame type, or a field a receiver must understand, that the peer has not advertised support for. This is the invariant that makes the unknown-frame default case safe to continue past. The gated frames are the record-lock control entries (`lockRelease` / `lockBarrier`, audit action nibbles 12 / 13, `isLockControlType`) and `RECORD_LOCK_HOMES_DIGEST`: `sendAuditRecord` skips a control entry, next to the `LOCAL_ONLY` skip, unless this socket has learned the peer's bag and it carries exactly the local `recordLocks` level (`peerSupportsRecordLocks`), and the skipped entry advances the peer's cursor like any other skipped record — a control entry that never arrives can only cost a requester a 423, never a second holder (see below). The digest announce is gated on the same condition.

**Observability.** The frozen result is mirrored on `NodeReplicationConnection.peerCapabilities`, replaced per socket — the slot must stay replaceable, since the object outlives the socket. `undefined` there means NOT YET LEARNED on the current socket, never "the peer does not support it": a peer that advertised nothing is the frozen defaults object, and a consumer gating on a capability must tell the two apart or it will deny a healthy peer mid-reconnect. Nothing is reported before a `NODE_NAME` lands, so a peer that wedges before its handshake is not misreported as pre-#646. The result is carried to the main thread on the existing `connected-to-node` message, deduplicated by field value. `applyConnectionMetadata` fences it with a `(worker thread id, per-worker session ordinal)` pair so a message from a replaced socket cannot overwrite the live entry; a wall clock cannot serve as that fence, since two workers can open a session in the same millisecond and a clock can step backwards. `cluster_status` reports the **effective** values per `database_sockets` entry as `peerCapabilities`, omitted while the shared-memory truth reads the socket down, plus `unknownCommandFrames`, omitted when zero. All of it is observability: the socket-local frozen object is the enforcement authority.

### Cluster record locks (`recordLockTransport.ts`, `recordLockRpc.ts`, `recordLockHomes.ts`, harper-pro#438 / #825)

Core (harper#2498, merged) owns the lock protocol — amortized per-record ownership, per core `resources/record-locks.md` ("Phase 1 design"; the § numbers below are that section's): a **home** per key derived by rendezvous hash from an **operator-agreed home map**, and a volatile **delegation** that serves repeat `lock()` calls from the local key lock with zero cluster messages. Only the release still rides the table's own transaction log (`lockRelease`, carrying the whole fencing token), and core's replicated-event sink applies it behind the data of its batch, with the author taken from the audit header's origin id, never from the payload. harper-pro adds **no receive path of its own** for that entry.

What harper-pro supplies is core's `ClusterLockTransport`, registered per replicated database on every thread by `assignReplicationSource`:

- **`homeMap(database)`** — read from a per-thread cache of this node's active generation, refreshed only when this node's own durable row changes (no storage I/O, hashing or sorting on the read path); each call reads every named peer's status slots 29/30 and returns a new `{ generation, homes, homeIncarnation }`. The map itself is **operator-agreed** (`recordLockHomes.ts`, harper-pro#825), never derived from `hdb_nodes` or capability advertisement: `undefined` unless this node has an active generation and a known `homeIncarnation` and **every peer named in `homes`** agrees — on protocol capability (see below) and on the home-map digest, an unknown answer counting as disagreement. A disagreement withholds the WHOLE map, not a smaller ring (excluding only the disagreeing peer would itself be a two-arbiter bug: with `homes = {A,B}`, A deriving `{A}` and B deriving `{B}` both self-home every key).
- **The §4.3 transition — durable storage plus an operator-timed protocol, not a node-timed one.** `hdb_record_lock_homes` is a dedicated `LOCAL_ONLY` system table, one row per database, holding `{ active?, staged?, highestActedOn, fenced[] }`. Five `super_user`-gated operations:
  - **`record_lock_stage_generation`** `{database, generation, homes[], quiesce[]}` — atomically retracts `active` in the same durable write that records `staged` (so the HTTP response IS real quiescence — this node stops granting under the old generation the instant the call returns, not after some later observed condition) and refuses a generation at or below `max(active, staged, highestActedOn)`. After that durable write it also **drains** (harper-pro#856): core's `quiesceDelegations` surrenders every delegation this node holds and recalls every grant it issued, and the result rides back on the response as `quiesced`, which is the only thing that lets an operator skip the drain interval rather than wait it out.
  - **`record_lock_fence_external`** `{database, node}` — the operator's audit-only attestation that an unreachable node was stopped outside Harper; no grant path consults it.
  - **`record_lock_activate_generation`** `{database, generation, homes[]}` — promotes `staged → active`, refusing unless it matches exactly what is staged (replay/consistency, never elapsed time). **Nothing in the code measures the real drain wait** (`DELEGATION_LEASE_MS + LOCK_LEASE_SKEW_MS`) — that is the operator's own external, wall-clock observation, anchored at the _last_ stage/fence across the whole affected set, which no single node can know. A small (`2s` default, `HARPER_TEST_RECORD_LOCK_MIN_DRAIN_BACKSTOP_MS`-overridable) backstop rejects an activation that arrives implausibly soon after _this node's own_ staging — defense in depth, not the safety mechanism. `RECORD_LOCK_HOMES_DESIGN.md` ("Approaches considered") records why a node-timed alternative was rejected (staggered delivery and non-immediate quiescence both reopen the two-holder bug; `Date.now()` is not a safe elapsed-time proof across a restart).
  - **`record_lock_apply_homes`** `{database, homes[], quiesce?[], generation?, drained?}` (harper-pro#862, `recordLockApply.ts`) — the one operator call that drives the whole transition over an explicitly supplied node list, over the node-principal hop `record_lock_transition` (re-validated on the receiving node). It refuses before staging on any incompleteness, and activates only when every node proves its drain or on an attested retry that covers only nodes already staged at its survey. Refusal table and retry contract: `RECORD_LOCK_HOMES_DESIGN.md` → "Applying a home map across the cluster".
  - **`record_lock_propose_homes`** `{database}` (`recordLockHomes.ts`) — **read-only**: writes nothing, notifies nothing, and is not agreement. Returns the home set this node's own `hdb_nodes` view suggests, the generation one past its own floor, the digest, `quiesce` (`homes(g) ∪ homes(g+1)`, so a shrink still drains the node leaving), the current `active`/`staged`, and warnings. `RECORD_LOCK_HOMES_DESIGN.md` → "Assembling a home map" has the two counterexamples that rule out a mutating bootstrap.
  - The digest (`digestOf`, `recordLockHomes.ts`; length-prefixed, never delimiter-joined) travels on a **dedicated wire message**, `RECORD_LOCK_HOMES_DIGEST` (not a `NODE_NAME` resend, which has untested side effects on reuse), sent at handshake and re-announced on every live outbound connection when this node's own active digest changes. Only a tri-state match/mismatch/unknown result lands in shared memory (**slot 30**, beside slot 29's support flag).
- **`homeIncarnation`** — core orders fencing tokens on `(generation, homeIncarnation, counter)`, so a home's incarnation must be durable and monotonic. Bumped once per **coordination incarnation** — a process start, or a genuine coordinating-worker handoff — not only at process start: `recordLockOwnerFor` itself gates a handoff, conferring ownership only after the bump durably persists (never while it is in flight), so a replacement worker cannot grant under a stale incarnation with its delegation counter restarted at zero. Workers never read the row themselves; they only adopt what main tells them over `record-lock-incarnation` (`setHomeIncarnation`).
- **`grantableAfterMono`** — core's own restart-quarantine waiver for a provably-first-ever incarnation (§4.3, the restart half), read once at coordinator construction and never re-read. Core builds that coordinator **lazily**, off any `TableResource.lockCoordinator` access (including a `cluster_status` poll), so the transport object must be rebuilt — forcing a fresh coordinator on next access — every time a fact `grantableAfterMono`/`homeMap()` depends on newly becomes true: this node's first-incarnation status known, ownership newly conferred, or the active generation newly available. Each is a distinct, independently-necessary trigger (`recreateRecordLockTransport`, called from `setHomeIncarnation`, `setRecordLockOwnership`, and `refreshCache` respectively) — missing any one of the three reproduces core's "restarted and cannot grant" 503 on every lock.
- **`requestDelegation` / `recallDelegation`** — two registered operations, `record_lock_delegate` and `record_lock_recall` (`recordLockRpc.ts`), sent over a live outbound subscription session to the home — this worker's own, or forwarded through main to the sibling worker holding one (harper-pro#977) — and only otherwise over `sendOperationToNode`, which opens a bounded connection per call; whichever of the home's workers accepts relays to its coordinator (next bullet). The requester's identity is the authenticated node principal of the connection, never the payload; a caller that is not a known node gets 403, so a `super_user` cannot mint or clear a delegation through the operations API.
- **Owner relay for inbound peer RPCs** — a delegate/recall/quiesce operation that arrives on a thread that does not own the database's coordination is relayed through the main thread (`record-lock-rpc` / `record-lock-rpc-reply`), which knows the owner, under a 5 s bound — except `quiesce`, whose owner-side sweep has its own `deadlineMs`, so its relay is bounded by that plus slack rather than by a flat 5 s that would discard a slow-but-successful drain. Main mints its own id for the forward hop, since worker-minted ids are per worker and would collide. A delegate relay that times out is answered `not-home`, which core treats as retryable inside the caller's own timeout and never as a grant; a recall or quiesce relay that times out fails with 503, since answering success would claim a drain that did not happen.
- **Owner relay for a local `lock()` (harper-pro#852)** — a `lock()` served on a worker that does not coordinate the database gets its admission from the one that does, over the **worker-to-worker port mesh** (`sendToThread`; main is not on this path, it only broadcasts which thread owns each database via `record-lock-owner-thread`). What crosses is the **admission**, never the handle: the calling worker keeps the native key, the staged writes and the lease timer, while the owner keeps the delegation. Core installs the owner-minted `LockRound` as a **remote admission** (`acquireOnOwner` → `#acquireFromOwner`), and a recall on the owner fences the caller's handle over the same mesh; the owner does **not** write the delegation `lockRelease` until the caller acknowledges the fence (or the handle's own lease elapses, past which it fences itself), preserving the §6 rule that no successor is admitted while a predecessor's staged write can still commit. A relayed admission is bound to an owner-session nonce and to the harness-stamped origin thread, so a release or ack that outlived an ownership handoff cannot address a same-numbered admission the new owner minted for another handle. The matching release is fire-and-forget (`releaseOnOwner`), the owner's lease being the backstop.
- **`ownsCoordination()`** — coordinator state is per worker thread while the key lock it arbitrates is process-wide, so exactly one thread per process may coordinate a database. The main thread assigns one owner worker per database (`recordLockOwnerFor`); subscriptions are placed round-robin regardless (`subscriptionManager.placeSubscription`), so the owner is usually **not** the thread applying the database's inbound entries. Ownership is conferred by message (`record-lock-owner`), not derived from `workerIndex`, and **moves only after the owner has exited**: a live owner still holds delegations and grants. A cluster-scoped `lock()` served on a non-owner http worker no longer answers 503 — it relays to the owner (above) — so the feature works uniformly at any `threads.count`. Before a successor is conferred, every worker is told the database is ownerless and must acknowledge that it fenced its relayed handles (`broadcastOwnerlessAndWait`); a live worker that never acknowledges fails the handoff closed and it retries, while a worker that **exits** counts as fenced. Two tempting arguments for that exit case do **not** hold. The coordinator's restart quarantine (`grantableAfterMono` / `#ownershipHorizon`) is consulted only where this node is the key's home, so a peer-homed key renews straight back to this node without ever reaching it. And the **native key lock** only stops two callers being _inside_ a critical section at once — a caller that staged a write and then unlocked has already returned the key while its write can still commit, which is precisely why `revokeLease()` fences capability rather than admission — so the window needs no teardown anomaly: any commit in flight when the worker exits reaches it. What does hold is the engine's **submission ordering**: an abandoned commit is not cancelled by its thread's death (measured: 40 000/40 000 still landed) but keeps its submission order (0/40 000 inversions against a successor writing the same key), so a successor admitted after the exit cannot be overwritten by the departed worker. The probe is `benchmarks/recordLockExitCommit/` (`npm run probe:record-lock-exit-commit`) and the writeup is `RECORD_LOCK_RELAY_TRANSPORT.md`. What is still open in rocksdb-js#865 is whether that ordering is _guaranteed_ across threads and across separate handles, rather than an artefact of one write queue on this build.
- **Control entries reach the owner by relay, not by placement (harper-pro#977).** Until #977 every subscription of a database was placed on its owner so core's replicated-event sink handed peer `lockRelease` entries to the coordinator on the applying thread; that put a single-database cluster's whole inbound apply on one worker whether or not anything ever locked (`integrationTests/cluster/recordLockPlacement.bench.mjs` reproduces it; its results are in the PR description, not committed). Now core's `#applyEntry` hands an entry it receives off the owner thread to the transport's optional `relayControlEntry` (`core/resources/recordLockCoordinator.ts`), which sends it straight to the owner over the worker port mesh (`record-lock-control-entry`, `relayLockControlEntry` / `handleRelayedControlEntry` in `recordLockTransport.ts`; `deliverLockControlEntry` on arrival), the same path a relayed admission takes. **The invariant that makes a best-effort relay sound:** the owner clears a grant only for the exact live token (generation, incarnation, counter) of the named delegate, and successor freshness is proven by the successor's own exact barrier, never by what the home applied — so a release that is late, reordered, duplicated or lost (owner unknown mid-handoff, port gone, mid-flight ownership change — the receiver drops anything for a database it does not coordinate) can only delay a re-grant until the grant's own deadline, which is what an off-owner drop already did. The relay fires from core's sink, **before** the enclosing batch commits (an applied barrier, by contrast, is reported from `onCommit`), so a batch that then fails to commit, or a worker that dies, can leave the home having cleared a grant whose release never landed locally: exclusion is unaffected, since the delegate fenced every handle before it wrote that release, and freshness still rests on the successor's own barrier — the local hole becomes poison or a held frame under the freshness design, never a clean admission. What stays counted: `droppedOffOwner` now means the transport had no relay or it threw; `controlEntryRelayDrops` counts entries the applying thread could not send (owner unknown there, port gone) plus entries the receiving thread refused (it no longer coordinated the database, or the sender was unstamped); `relayedControlEntries` on the owner's entry counts what arrived. **Trust boundary:** the relayed `author` is core's resolved audit-header origin, carried by a sibling thread's message; that thread is trusted on the same basis as the rest of the process, since in-process code already reaches the coordinator directly (`Table.lockCoordinator`) — the mesh adds no authority. The counterpart: a lock RPC the owner sends (delegate, recall, barrier) usually finds no live session on its own thread any more, so `sendRecordLockOperation` forwards it through main to the worker holding that (peer, database) subscription (`record-lock-rpc-out`, one absolute deadline carried through every hop; `cluster_status.recordLocks[db].outbound` counts `session` / `forwarded` / `fresh`), and only a topology with no session anywhere opens a connection per call. A delegate request is bounded by `MAX_LOCK_TIMEOUT_MS` plus slack — longer than any lock wait, so core's own deadline fires first and a grant that arrives late is still handed back to the home (`#requestRemotely`); a recall by the delegation lease. Either bound keeps a silent peer from pinning a hop or a socket.

**`recordLocks` capability, versioned and mutually exclusive.** Level 1 was Ricart–Agrawala (harper#2498 before its replacement) and never shipped enabled; level 2 was delegations against core's now-superseded static-epoch interface and never shipped enabled either; level 3 was delegations against core's operator-agreed `homeMap()` interface; level 4, the current one, adds successor freshness (`protocolCapabilities.ts` records what each level carries). `peerSupportsRecordLocks` requires the level exactly rather than "at least 1": a cluster running two would have two independent arbiters for one key. Capability level and home-map digest agreement are checked **independently** in `homeMap()` — a coincidentally-matching digest from a peer at the wrong protocol level is not enough.

**`replication.recordLocks` (default off).** It is an explicit opt-in because it advertises a capability every peer must match exactly and nothing locks until an operator activates a home map; it no longer changes subscription placement (harper-pro#977, above). Off, replication is unchanged except that dropped records are still recorded as poison (`recordReplicationHole` is not gated on the switch; see `RECORD_LOCK_FRESHNESS_DESIGN.md`, "Cost"), the node advertises `recordLocks: 0`, and every replicated database gets a transport whose `homeMap()` refuses with a 503 naming the switch (`createDisabledRecordLockTransport`) — a cluster-scoped `lock()` fails closed rather than quietly arbitrating on one node, while `{ scope: 'node' }` keeps Phase 0 semantics. Even ON, nothing locks until the operator explicitly stages and activates a generation (above) — enabling the switch alone is not enough, by design.

**Observability.** `cluster_status` gains `recordLocks: { [database]: { ownerThreadId, delegations, granted, admitted, droppedOffOwner, relayedAdmissions, relayedControlEntries, controlEntryRelayDrops, outbound: { session, forwarded, fresh }, members, freshness, poisoned, unprovenMs } }` (`RecordLockDatabaseStats`, `recordLockTransport.ts`), gathered by the main thread from every http worker under a one-second bound (`collectRecordLockStatus`; `droppedOffOwner` and `relayedAdmissions` are summed across every worker, and across main when it served an off-owner `lock()`). `relayedAdmissions` is the count of admissions a non-owner thread obtained from the owner over the harper-pro#852 relay — the metric that makes multi-worker lock service visible. `members` is the home map's `homes` as the owner sees it, or absent while the map is withheld (no active generation, or a peer disagreement). `relayedControlEntries` and `outbound` are the owner's; `controlEntryRelayDrops` is summed across every worker (harper-pro#977).

**Measurements** (not gates; each file names its bench and machine):

- `RECORD_LOCK_COST_BASELINE.md` — the superseded Ricart–Agrawala protocol on a 3-node mesh (`npm run bench:record-locks`). A before-figure, not a description of this transport: repeat-lock p50 0.68 ms.
- `RECORD_LOCK_COST_DELEGATIONS.md` — the delegation protocol (harper-pro#824): repeat-lock collapses to 0.01–0.03 ms; a contended key is monopolized rather than shared; before the freshness barrier (harper#2542) the hot-key counter lost 0.05–0.13 % of updates at 3 contenders.
- `RECORD_LOCK_RELAY_TRANSPORT.md` — the off-owner relay (`npm run bench:record-lock-relay`). A relayed acquire costs the coordinating worker's turn length (0.0164 ms idle, **1.008 ms at 1 ms of work per turn**, above the 0.68 ms round trip delegations replaced, for `(N-1)/N` of locks). `notify()` is no faster than `postMessage`. A local admission against a `getUserSharedBuffer` slot (0.0002 ms) is a follow-up that adds a fast path but cannot remove the revoke/ack fence, because a handle is revoked after `unlock()` has already returned the key (`recordLock.ts` `revokeLease()`).

**Successor freshness (harper#2542, core half harper#2613, fence harper#2625).** A handoff now carries freshness as well as exclusion: core hands the transport the inherited `(origin, position)` lineage of a grant, and `establishLockFreshness()` (`recordLockFreshness.ts`) proves each cross-origin dependency by asking the origin for a `lockBarrier` control entry (`record_lock_barrier`, `recordLockRpc.ts`, node principal + current member at the exact level, rate-bounded) and waiting for that exact `(origin, position, nonce)` entry to commit here — reported from the frame's `onCommit` in `replicationConnection.ts`, relayed to the coordinating thread when applied elsewhere. Nothing numeric is a fence (rocksdb-js appends in commit order and reissues keys after a clock step), so ordinary frames pay only a type comparison. A record this node drops (excluded table, missing structure, decode error) or fails to apply terminally (core's awaited listener, harper#2628) poisons `(origin, table)` durably and permanently (`recordLockPoison.ts`), except when the poison write itself fails — then the hole is held only in that thread's memory (`RECORD_LOCK_FRESHNESS_DESIGN.md`, "Poison"); a clone attempt sets an ever-recloned flag before its first row, after which this node's own earlier lineage is refused. Every refusal is a 503 naming the reason; `cluster_status.recordLocks` carries the counters and poisoned pairs. The full design, the append-order probe and the rejected alternatives are in `RECORD_LOCK_FRESHNESS_DESIGN.md`; the planning rounds are in harper-pro#822's description.

**Multi-worker service (harper-pro#852).** Two items core's §11 left owed are now closed. Every-serving-thread registration holds by construction: the transport registers from the replication built-in's `start()`, and a built-in is a trusted plugin `placedOnThisThread` loads on every http worker (dedicated application workers included), so every serving thread latches `clusterRequiredDatabases` and fails closed rather than taking the Phase 0 node lock alone. A `lock()` on a non-owner worker relays its admission to the owner (see the owner-relay bullet), so cluster locks work uniformly at `threads.count > 1`. The `recordLockHomes` row transition also moved to a **process-wide** guard: `withRow` takes a node-scoped hold lock on the `hdb_record_lock_homes` row itself and writes **through** that locked handle, so the read a `stage`/`fence`/`activate` decides against and the write that replaces the row are one cross-thread-exclusive critical section, and a lease lost to a storage stall fails the write (commit fence) rather than letting a stale plan overwrite a concurrent transition. The last §11 item, the inbound-peer `lockRelease` cross-thread relay gap, is closed by harper-pro#977 (the control-entry bullet above). A crashed delegate holds its keys for up to `DELEGATION_LEASE_MS` (a core constant) before its home re-grants them; whether it should be configurable was left open on harper#2498.

### `Replicator extends Resource` (`replicator.ts`)

A `Resource` class installed as a `source` of a table. Declared inside `setReplicator()` and passed to `table.sourcedFrom(...)`. Its `static async load(entry)` method picks the lowest-latency available node for cache-miss fetches.

### Shared status buffers (`getReplicationSharedStatus` in `knownNodes.ts`)

Per (database, remote_node) pair: a `Float64Array` over the audit store's `getUserSharedBuffer`, shared across threads, used to avoid IPC for hot-path status updates. Every position is allocated, in this order, by one dependency-free registry module, `sharedStatusSlots.ts` (harper-pro#885) — a `let cursor` incremented once per exported constant, so two slots cannot collide by construction and the next free one is whatever the file's last line leaves in `cursor`. `replicationConnection.ts` and `recordLockTransport.ts` import their constants from it and re-export them unchanged, so existing import paths (and this table) still hold:

The buffer is 64 `Float64` slots (512 bytes, `REPLICATION_SHARED_STATUS_SLOTS` in `sharedStatusSlots.ts`, re-exported from `knownNodes.ts`) — 0–31 are used as above (30 is the record-lock home-map digest agreement tri-state; 31 is the peer's exact advertised `recordLocks` level); 32–63 are headroom for the peer-scoped transport (harper-pro#884) and the ownership domain (harper-pro#886). **A new slot is added in `sharedStatusSlots.ts`, never hand-numbered in an owning module**: `unitTests/replication/sharedStatusSlots.test.mjs` walks the TypeScript AST of every file under `replication/` (recursively) for a `*_POSITION`, `*_SLOT` or `*_INDEX` declaration outside the registry, asserts every allocated position is distinct and in range, that the fire-counter block doesn't reach its neighbors, and that the allocator throws rather than silently exceeding capacity. Slots 0–12 are written concurrently by `replicationConnection.ts` without explicit synchronization (single-writer-per-field in practice) — **don't introduce read-modify-write patterns on those.** Slots 13–28 are the one deliberate exception; see the counter invariant below.

The buffer size is fixed once, at this process's build, for the process's whole lifetime — nothing in this codebase resizes an existing (database, peer) buffer while a process runs, so growing the constant is safe across a restart. A **live** resize is not available: probed against both lmdb-js and `@harperfast/rocksdb-js`, a second `getUserSharedBuffer` for an already-registered key returns the **first** buffer at its original size and ignores the larger default — no throw, no resize — so writes past that length land outside the typed array and are silently dropped. The first registration of a key within a process therefore fixes its size for that process, and growing `REPLICATION_SHARED_STATUS_SLOTS` takes effect only on restart. Every caller must pass one size per key, which is why the capacity is read from the registry inside `getReplicationSharedStatus` rather than supplied by callers (`unitTests/replication/sharedStatusSlots.test.mjs` pins that).

**Connection truth (W1 / harper-pro#431).** Slots 9–12 make the owning worker thread the authoritative source for an outbound subscription's link state, rather than relying solely on the edge-triggered worker→main `postMessage` mirror (`connected-to-node` / `disconnected-from-node`), which desyncs when a terminal/idle state is reached without a `'close'` (open-but-idle wedge, #289/#233). The worker writes `CONNECTION_STATE_CONNECTED` + `LAST_LIVENESS_TIME` on pong and on received data, `CONNECTION_STATE_DOWN` + error on close/`forceReconnect`, and refreshes liveness during a backpressure pause (matching `shouldTerminateIdlePing`'s `pauseReasons` exemption). The main thread reads it via `deriveConnectionTruth` / `readConnectionTruth`: `connected` requires `CONNECTED` **and** fresh liveness (`< LIVENESS_STALE_MS`, derived from `PING_TIMEOUT`), so a worker that died/wedged without writing `DOWN` still reads down once liveness goes stale. `clusterStatus.ts` reports it (authoritative `connected` + `lastConnectionError`); `subscriptionManager.ts → reconcileWorkers` corrects the inferred flag against it, feeding the existing wedge recovery.

**Lifecycle invalidation (W1 residuals R1/R2, harper-pro#431).** A worker that dies cannot write its own `DOWN`, so the main thread stamps it: `LAST_ERROR_CODE_POSITION` takes `WORKER_EXIT_ERROR_CODE` (100001 — deliberately outside the 16-bit WebSocket close-code space, so `lastConnectionError` distinguishes "the owning worker died" from "the peer closed us") with `LAST_ERROR_TIME`, while `LAST_LIVENESS_TIME` is left as the record of when the dead link was last proven alive. Two writers stamp it under the same ownership guard — only a worker OBJECT that has left the live replication pool (`replicationWorkers()`) is stamped, so neither a successor nor a main-thread-owned entry (`worker: undefined`, created when the pool was empty) can be downed: the worker `'exit'` handler (via `clearWorkerFromEntries`' owned-entry callback, fired while the dead worker is still the recorded owner) and `reconcileWorkers`, per entry, via `hasDeadOwner`. The second is defense in depth and rarely reached: `manageThreads` splices a worker out of `workers` in its own `'exit'` listener, registered at creation so it runs first, and `clearWorkerFromEntries` nulls `entry.worker` in that same synchronous emit — so a tick sees "worker object present, absent from the pool" only for an entry whose worker never got an exit handler. Note what that does NOT cover: a worker that is wedged but still in `workers` is indistinguishable from a healthy one here, and its links read down only once liveness goes stale. The stamp only survives because the buffer does: RocksDB frees a user shared buffer's backing allocation once every view of it is collected (LMDB keeps it for the env's lifetime), and the owning worker's view is otherwise the only durable one — so the whole buffer, not just the stamp, is re-minted as zeros when that worker dies. The main thread therefore holds a view on the `connectionReplicationMap` entry (`sharedStatus`): taken before the subscribe is dispatched, re-taken on every `onDatabase` pass and every `reconcileWorkers` tick so a renamed peer or a recreated database is followed, carried across a dead-owner reassignment, and released with the membership. A database not yet visible to the main thread resolves nothing, leaving the worker sole holder until its schema arrives.

Removal zeroes the buffer from the main thread in `onNodeUpdate(null)`, via `clearReplicationSharedStatus`. That is the only writer of the clear, and it depends on the departing connection being cut off from the buffer: `unsubscribe()` merely _starts_ the teardown, and the close it triggers stamps `DOWN` + close code 1008 through the connection's retained `sharedStatus` view — gated only on `nodeSubscriptions`, which unsubscribing never clears. Since no `CONNECTED` writer ever clears the error slots, that stamp would otherwise stick on a re-added link's buffer and `cluster_status` would report a failure the new membership never suffered. `releaseSharedStatusOnUnsubscribe` (`replicator.ts`, on the removal path only) drops that marker. `unsubscribeFromNode` retires the cache entry and that marker _before_ attempting the transport close, so a `close()` that throws cannot leave the departing connection still owning the buffer; the throw is contained in `unsubscribeFromNode` because every call site dispatches it fire-and-forget and a rejection would otherwise reach only the process-wide `unhandledRejection` handler, which cannot name the node. The two ownership branches order it differently: for a main-thread-owned entry `unsubscribeFromNode` runs inline, so the release precedes the clear; for a worker-owned one it is deferred behind the port message, so socket events already queued ahead of that message can re-stamp for one event-loop turn after the clear. That residual window is known and accepted — closing it means gating the hot-path write sites on current ownership. It deliberately does not clear as well: a same-process re-add can be assigned to a different HTTP worker, whose connection this one cannot see, and that successor's `CONNECTED` stamp must survive. `reconcileWorkers` also checks each tick for a tracked peer that is no longer in `nodeMap`, reporting each such pair once — but note it is a narrow backstop, not a general one: the removal path deletes the entry the check iterates, so the reachable case is the same-URL rename window in `onNodeUpdate`, not removal.

**Link-metric bridge (W1 residual R3, harper-pro#431).** `reconcileWorkers` copies `LATENCY` and `BACK_PRESSURE_RATIO` off the same buffer read it derives truth from onto the main-thread entry, and `cluster_status` publishes both — this is the bridge adaptive routing (#218, W5) consumes. `LATENCY` is copied only when truth reports the link connected, because it is the one slot here that cannot be owner-gated at the writer: `replicator.ts`'s cache-miss picker chooses a peer by the reading a RETRIEVAL connection leaves there, so the pong write at `replicationConnection.ts` stays open to every connection resolving the same (database, peer) key. On a link truth reports down the owner is not ponging, so a fresh reading is some other socket's RTT; the entry keeps its last owner-era value instead. On a connected link the copied sample can still be an inbound socket's — same peer, same path, so it is a sample of the link rather than of a different one. `BACK_PRESSURE_RATIO` needs no gate: its writer already requires `nodeSubscriptions`.

**Fire-classification counters (W1 residual R4, harper-pro#431).** Slots 13–28 hold one `{redundant, loadBearing}` pair per recovery mechanism, in the order of `FIRE_MECHANISMS` (`receive-watchdog`, `pause-stall`, `copy-progress`, `blob-gap`, `copy-finalize`, `subscription-setup`, `wedge-reconcile`, `receive-stall-net`), based at `FIRE_COUNTER_BASE_POSITION`. `FIRE_MECHANISMS` is **append-only**: the index picks the slot pair, so reordering or removing a name reassigns existing counters. At every fire the mechanism records whether shared-memory truth also judged the link down (`redundant`) or not (`load-bearing`); a fire records `unknown` and increments neither when it comes from a connection that does not own the (db, peer) subscription (an inbound server socket, a cache-miss retrieval connection), because that buffer describes a different link, or when truth has observed nothing at all — no liveness and no recorded error — because scoring that as `redundant` would claim a detection that never happened. `clusterStatus.ts` surfaces them as `recoveryFires`, and each fire log line carries `fire={mechanism: …, class: …}`. This is measurement only: no net is demoted, no threshold moves, and no fire predicate consults it.

> **Counter invariant.** The `+= 1` on slots 13–28 is read-modify-write on an unsynchronized shared buffer, and is safe only because **each mechanism's slot pair has one writer thread per (database, peer)** — the six worker-local watchdogs write only from the connection that owns that subscription (the `unknown` classification is what keeps every other connection out), and the two reconcile nets write only from the main thread. One exception is known and accepted: during a reassignment the departing worker's connection still holds `nodeSubscriptions` (only the removal path clears it), so two owner connections can briefly overlap. The cost is a lost increment, not corruption. No pair is shared between mechanisms; `unitTests/replication/fireCounters.test.mjs` pins that disjointness. Adding a mechanism means adding a pair, never sharing one.

**Record-lock capability (harper-pro#438, W9 Phase 1).** Slot 29 (`RECORD_LOCKS_CAPABILITY_POSITION` in `recordLockTransport.ts`) holds whether the peer at the other end of this (database, node) pair supports record locks — `LOCK_CAPABILITY_UNKNOWN` / `_UNSUPPORTED` / `_SUPPORTED`, supported meaning exactly the local level (slot 31 holds the level itself) — so the owning worker can read a peer's capability even when that peer's socket lives on another thread. Written by `recordPeerLockCapability` on handshake, read by `readPeerLockCapability`; an absent value reads as `LOCK_CAPABILITY_UNKNOWN`.

## Backoff discipline (harper-pro#327)

Every retry/reconnect initiation site paces attempts through **one** utility, `createBackoff` in
`backoff.ts`: an exponential ceiling with **full jitter** (uniform draw across the window) by default,
an optional fixed floor, an optional wall-clock/attempt budget, and injectable RNG/clock so every bound is
deterministically testable. An exhausted schedule returns no delay rather than `0`, so a missed exhaustion
check cannot create a busy loop. Before this there was no jitter anywhere in production code — a fleet
reacting to one event retried in lockstep — and the delays themselves ranged from flat 200 ms to
jitterless doubling.

The invariant the discipline enforces: **at most one pending attempt per target, on a bounded, capped,
decorrelated schedule.** Pacing alone is not enough; the storm surface below needed the dedup too.

**A sweep slide counts only if it advances the fire time.** Fire times are `performance.now()` plus an
integer delay, so just below a power of two `armedAt + RECONNECT_STAGGER_MS` can round back inside the
window, and a slide that re-assigns that same time never terminates — on the main thread. Requiring strict
advance through the sweep's finite set of armed times bounds the slide at one move per armed setup
(`subscribeSetupScheduler.test.mjs` pins the rounding case).

**The subscription-setup scheduler is the one with dedup.** `onDatabase` used to turn every qualifying
node update straight into a retained (not unref'd) 200 ms `setTimeout` plus a `subscribe-to-node`
message, so whatever re-drove `onNodeUpdate` amplified 1:1 into main-thread timers, worker-side
WebSocket/TLS setup, and `Setting up subscription with leader` warns — ~1,400 lines/s/node in the field,
ending in an OOM kill. The scheduler holds one armed setup per **(peer URL, database)** in its own map
(_not_ on the `connectionReplicationMap` entry, which the stale-worker path deletes and recreates), and
the armed setup carries the newest level-state payload — `onDatabase`'s early-return path refreshes
that payload without arming another timer, so a pending setup observes the latest routing, leadership,
and exclusion state. Self-catchup is separate one-shot state: the first dispatch claims it for one
connection entry, which keeps the bounded rider for its life and reattaches it until the owning primary
connection opens. That worker then re-sends it on its own reconnects, so recovery re-drives to it stop
carrying it: the rider's old `startTime` becomes the leader's `min(startTime)` and costs a scan from there to
now. A replacement worker (a recreated entry) is sent it again, because the main thread cannot see catchup
finish and a worker that exits mid-catchup would otherwise take the range with it — one scan per worker
replacement. A same-worker wedge re-drive after the open still replaces the worker's subscription list
without it, as `main` always did. The global claim is consumed only after the worker message
is accepted, so timer cancellation, entry refresh, a long offline retry, or a synchronous `postMessage`
throw cannot lose or overwrite it.
A setup is cancelled on
unsubscribe, on node deletion, and on a same-name URL migration, all of which became reachable once a
pending timer could live 30 s instead of 200 ms. The wedge/stall recovery kicks are owned the same way —
one `entry.reDriveTimer` per entry, so a staggered sweep that outruns the reconcile window that started it
keeps the already-armed attempt instead of restamping it out of existence, and disarms it when the owning
worker exits or the entry is replaced.

**A connect report cancels nothing; every report resets the pair's escalated setup delay.** Gating that reset
on entry ownership let a chaos-restart peer's delay escalate past its reconvergence budget. A worker can
carry both the primary and a proxied failover connection, so a socket-open report (`newSocket`) carries its
thread id and subscription URL; only the owning worker's primary open advances `connectGeneration`, as does a
truth up-correction, which stands in for an open edge that never arrived. Pongs and proxy/superseded opens
still perform the pair-level reset but cannot cancel a stall kick. What makes leaving
the timers armed safe is that each re-checks live state when it fires: the
setup re-reads the entry and its `unsubscribed` flag, the wedge kick claims its entry through the
`disconnectedAt` stamp a connect clears, and the stall kick claims it through `connectGeneration` (a stalled
connection is `connected: true` with no `disconnectedAt`, so the stamp cannot discriminate for it), the
captured worker identity, and the receive watermark. `shouldFireStallKick`
holds that decision, because the stamp it checks is also the re-detection throttle: a kick skipped because
the leg reconnected has to hand the stamp back, or a fresh socket that stalls too is never detected — its
`lastReceivedTime` can never move past a stamp it never advanced.

Their jitter is drawn once
per sweep rather than per entry: a per-entry draw would vary consecutive delays by up to ±200 ms and let
several dials share a 50 ms instant, which is the concurrency the `RECONNECT_STAGGER_MS` spacing exists to
bound (#446). The warn moved inside the "actually armed" branch: it now describes an attempt, not an
event.

The worker boundary has one additional admission point for its asynchronous startup window. Before
components are ready, one insertion-ordered map retains only the latest subscribe/unsubscribe message
per actual connection key and database, with one continuation on the readiness promise — and, if that
readiness rejects, exactly one armed re-attempt on the same schedule, so the retained actions apply without
waiting for another message or the wedge reconcile. After readiness,
the handlers run inline and allocate no queue state; the existing connection map is then the single-flight
owner. Subscribe, unsubscribe, force-reconnect, and startup admission all derive the connection key through
`getSubscriptionConnectionKey`, including the missing nested-URL fallback.

An armed setup dispatches on the main thread only in configured single-thread mode. If its worker exits
before it fires in a multi-threaded process, the setup is deferred; the stale-worker reconcile reassigns the
entry even when another database for the same peer is simultaneously in wedge recovery.

**The reconnect backoff resets on progress in either direction, never on socket open.** A leg that reopens and
fails before moving data — a peer that accepts TLS and drops it (harper-pro#339), or a stream blocked at an
oversized frame (#713) — must keep escalating. The sending side resets in `onFrameSent`. A subscriber's
outbound leg sends no transaction frames (in a two-way mesh the peer serves our subscription from its own
server session), so it resets through `onDurableProgress` when its receive-side durable watermark advances: at
a commit and at the last in-flight blob's drain. Three things keep that from resetting a leg that is not
working. Only an advance past the highest valid clock this `NodeReplicationConnection` has already credited
counts, so replaying the same undurable frames after each reconnect is not progress. Nothing counts while a
copy-apply copy is in progress, because its rows are not durable until the copy's final flush; finishing the
copy counts. And a sender-loop failure on the leg (`onSendFailed`) vetoes receive credit until the sender
sends a frame or catches up (`onSenderCaughtUp`, which then applies any credit it held back), so a leg that
both receives and serves a subscription does not redial at the floor while its own sends fail every time — a
loop stuck on an oversized frame does neither. Only the session that still owns the socket reports any of
these. Without the receive signal, the ceiling carried across unrelated outages until every reconnect waited
out the 30 s cap (`connectedBitRestartChurn.test.mjs`). Still open: a leg that receives nothing new between
outages (idle, or mid-copy) carries its escalated ceiling into the next one.

**What is deliberately NOT on this schedule:** the receive/copy watchdogs and their thresholds, and the
doubling copy-finalize _timeout bound_ alongside them (these _detect_ stalls or bound a wait; this
discipline paces _retries_, and jittering a durability deadline would be actively wrong),
`blobGapReconnectTimer`, `PING_INTERVAL`/`PING_TIMEOUT`, and `RECONCILE_INTERVAL_MS`.

## Non-obvious behaviors

1. **Auth failures don't send DISCONNECT.** When the `authorization` promise rejects in `replicateOverWS`, the connection closes with "Unauthorized" but no DISCONNECT frame is sent — the client is expected to retry.

2. **A skipped record still advances the peer's cursor.** `sendAuditRecord` skips a record the subscriber must not receive (`LOCAL_ONLY`, a gated lock control entry, an unsubscribed or excluded table, an origin the subscription does not cover, a residency omission). Every skip branch returns `skipAuditRecord()`, which yields (#536) and, at most once per `SKIPPED_MESSAGE_SEQUENCE_UPDATE_DELAY` (300 ms), sends a `SEQUENCE_ID_UPDATE` when the last sent sequence id has fallen behind, so a long skipped run still moves the peer's resume cursor.

3. **Blob back-pressure, transfer identity & timeout.** Blobs time out after `blobTimeout` (default 900s); concurrent sends are capped at `MAX_OUTSTANDING_BLOBS_BEING_SENT` (`replication.blobConcurrency`, default 5); back-pressure ratio (computed every `BACK_PRESSURE_INTERVAL`) tells senders to pause. Copy-mode `BLOB_CHUNK` headers carry an optional `transferId` so adjacent records that reuse one file id do not share skip/apply receive state. A current receiver keys those streams by `transferId`; an older sender omits it and the receiver falls back to `fileId`. Distinct records intentionally get distinct transfers, even when they reference the same file, because a skipped record must not consume an applied record's only transfer; those sends are serialized by file id for older receivers, and receive-in-flight markers are refcounted by file id. The identity-tie fast path proves only uncompressed blobs whose header and file length agree; compressed blobs fail closed because their completeness requires core's writer lock. Transfer ids come from a module-lifetime counter rather than resetting per connection, and their enumerable blob tag exists only inside the synchronous record encode's `try`/`finally`; it must never remain on the process-cached stored record. If you're seeing large-data replication hangs, look here first.

4. **Shared-buffer concurrency.** The status buffers have no lock and no change notification; treat them as eventually consistent. Writer rules: "Shared status buffers" above.

5. **Per-route table exclusion (`excludeTables`).** Route entries in `sendsTo`/`receivesFrom` can specify `excludeTables: ['hdb_nodes']` to prevent specific tables from crossing the wire. Three layers enforce this: (a) subscriber omits them from SUBSCRIPTION_REQUEST (in `sendSubscriptionRequestUpdate`); (b) sender skips their audit records before streaming (in `sendAuditRecord`); (c) receiver drops any that arrive (in the incoming message loop). Route config `routeReplicates` is threaded from `subscriptionManager.ts` onto `nodeSubscriptions` objects so static-route exclusions are available inside HTTP worker threads where `replicateOverWS` runs. Primary use case: v4→v5 migration bridges that share `system` database users/roles but must keep per-cluster `hdb_nodes` topology tables isolated.

6. **Keep-alive is measured from byte activity, not a single ping interval.** `shouldTerminateIdlePing` terminates a connection only after no socket bytes have moved in either direction for the full `PING_TIMEOUT`. A bulk transfer — notably the initial clone copy of a large table — makes slow but real progress (the sender's buffer drains in bursts as the peer consumes), so bytes keep moving within the window and it is not killed mid-copy (the old "no bytes since last ping → terminate" heuristic restarted the copy from zero — issue #241). A genuinely dead peer moves no bytes and still trips the timeout — including the case where the sender filled its socket buffer and the `drain` event never fires. The sole exemption is `pauseReasons > 0` (the receiver intentionally stopped reading to drain its own queue): that stall is local and self-clearing, so the caller keeps liveness fresh while paused. That paused window is not left unguarded, though — the byte watchdog is _blind_ while paused (`ws.pause()` freezes `bytesRead`), so a companion **pause-stall watchdog** (`createPauseStallWatchdog`, armed on pause / stopped on resume) takes over, keyed on a local consumer-progress counter (`onCommit` + blob-drain ticks) that keeps advancing while paused. A pause that is making progress re-arms every window; only one with ZERO consumer progress for `PAUSE_STALL_THRESHOLD_MS` (it can never self-clear) forces a reconnect — closing the hole where a leg that died mid-pause (e.g. a base copy stalled at ~100% back-pressure) had no recovery driver at all (harper-pro#466). Relatedly, the receive decode loop in `replicateOverWS` yields the event loop on a time budget (`RECEIVE_YIELD_INTERVAL`) — not only when the consumer queue exceeds `RECEIVE_EVENT_HIGH_WATER_MARK` — so a single large message can't decode in one synchronous turn and starve ping responses (core's `MAX_EVENT_DELAY_TIME` monitor).

7. **The initial bulk clone copy is resumable (PK cursor).** When a follower requests a full copy (`startTime: 0`), the leader sends `COPY_START{copyStartTime}`, walks each table's primary store in key order, flushes a checkpoint transaction every `COPY_CHECKPOINT_RECORDS` (timed at `copyStartTime` so the persisted `seqId` stays pinned there, never a record's `localTime`), and sends `COPY_COMPLETE` at the end. The follower persists a cursor `{copyStartTime, currentTable, afterKey}` under `dbisDB` key `[Symbol.for('copyCursor'), nodeId]` (one per source peer) — staged in the `end_txn` `onCommit`, **after** the batch commits, and written only once a RocksDB flush has made the copied rows durable (harper-pro#480), so the cursor can never get ahead of committed data (a resume re-copies a few records idempotently but never skips). On reconnect, `sendSubscriptionRequestUpdate` reads the cursor and sends it as `copyResume` on the subscription request (overriding the persisted `seqId`, which alone would skip the un-copied tables); the leader skips tables before `currentTable` (stable iteration order ⇒ already committed) and resumes `currentTable` after `afterKey`. `COPY_COMPLETE` clears the cursor so subsequent connections resume normally from `seqId`. Before this, an interrupted copy restarted from zero and never converged for a large table (issue #241).

   **A base copy never returns the requesting peer's own records while we are cloning from it (harper-pro#737).** While a clone attempt is in flight, and for a bounded 60-second grace after synchronization completes, `cloneNode/cloneAttempt.ts` reads BOTH `HARPER_CLONE_ATTEMPT` in this process and the `.cloneAttempt.json` marker on disk. Each covers the other's failure mode: worker threads copy the environment at spawn, and a plain `harper run` restart never enters the clone path, so a marker left by a killed process authorizes nothing. A completed marker carries `completedAt`; the reader fails open after the grace even if its best-effort cleanup fails, and a later clone mints a new attempt id instead of reusing completed state. During that window, a base copy to the peer this node holds `isLeader` for, and whose host the marker records as the clone source, skips every record that peer originated (`entry.nodeId`, the same origin the copy stamps). It already has them, and each redundant apply back on a legacy v4 leader mints an audit entry v4 cannot decode: v4's apply passes `previousVersion = 1`, lmdb-js's instructed-write substitution writes `2.0`, and the field's only presence signal is a leading `0x42` byte (a float64 in the ms-timestamp range), so every reader skips the 8 bytes and parses the entry offset; v4's own forwarding then reads `recordId` out of the misaligned region and throws `BigInt(non-integer)`, closing the subscription 1008 in a reconnect loop. v4 asks for this copy on its own: its leader heuristic is ungated (`isLeader = !leaderCandidate || nodeName === leaderCandidate`, the candidate falling back to "the first other node in hdb_nodes"), so during a v4 → v5 clone it concludes the clone is _its_ leader. harper-pro stopped guessing that in #254; the legacy peer cannot be fixed, so the filter lives on the serving side, the only place a v4 peer can still be answered. Filtering by origin rather than skipping the copy is what keeps it lossless: records this node authored or received from a third node are still copied, so the trailer never claims a copy completed while rows the peer lacks were withheld. Leadership is read from the authenticated peer's local `hdb_nodes` row, never the peer-controlled subscription payload. The window is narrow in practice for a reason worth knowing, and it also bounds what can be tested: a peer only asks for a base copy when it has no resume cursor for this node, and the first record of ANY origin that reaches it from us gives it one — so the reverse copy is reachable only before the clone has sent the leader anything, and no integration test can seed a differing-origin row into the clone without also disarming the path under test. Three gaps are knowingly left: a v4 leader whose reverse connection lands after the completion grace still receives a full copy (including a reconnect whose earlier attempt was withheld, since v4 cannot resume a copy and the gate is re-read per copy); an outside restart inside the grace loses it, because the config already reads `cloned: true` so the new process skips the clone path and never sets `HARPER_CLONE_ATTEMPT` (the stamped marker alone does not authorize withholding); and a v4 _cluster_ leader still receives back rows a third v4 node originated (the wedge trigger is a redundant apply of anything the peer already holds, which the copy protocol cannot know). The same latent format hole also exists in core's `createAuditEntry`/`readAuditEntry` for a v5+LMDB audit store. All three gaps describe this origin-withholding mechanism in isolation; for any capability-less peer (v4 or otherwise) they're now moot, since `safeCopyAudit` verification below bypasses withholding entirely and sends such peers zero historical rows, not a full copy.

   **The anchor is a position in the log's append order, not a timestamp (harper-pro#876).** A
   transaction's log key is fixed when the transaction is **created**; its log batch is appended when it
   **commits**. The log is therefore written out of key order — measured at 47 inversions per 1000
   concurrent transactions — so a `Date.now()` anchor was never a boundary in it: a transaction created
   before the anchor and committed during the copy sits _behind_ it numerically and _after_ it
   physically, and the post-copy tail's per-entry predicate
   (`exclusiveStart ? timestamp > start : timestamp >= start`, in rocksdb-js's `TransactionLog.query`)
   excluded it while the key-order walk had already passed its row. Permanent loss, and the same
   reasoning `RECORD_LOCK_FRESHNESS_DESIGN.md` records for fences: _nothing numeric is a fence_.

   The leader anchors on **the key of the latest committed entry in its `local` log**, read just before
   `COPY_START` (`findLastCommittedLogKey`, which bisects on key with one pulled entry per probe — a
   range seeks through the log's running-max index, so no probe reads history). The log yields
   entries only up to its committed watermark, which rocksdb-js advances past a transaction only after
   its RocksDB commit succeeds, and only across a contiguous prefix — so everything up to the anchor
   is visible to the walk, and everything still in flight appends after it. The copy's tail resumes
   with `exactStart` + `resumeAfterExactStart`, after which the predicate stops consulting the key at
   all. That range is built **before** the walk, because `getRange` resolves the position and maps the
   log file eagerly, and it is validated by pulling a throwaway copy of the same range —
   `exactStartFailures` is filled during `next()`, so an unpulled iterable cannot answer. `exactStart`
   is scoped to `local` by `startByLog`, so the other logs in the aggregate are untouched. Gated on
   `auditStore.reusableIterable` (the RocksDB log store), not the `STORAGE_IS_ROCKSDB` config
   snapshot, which can misreport the engine in a worker.

   An empty log needs no anchor entry: everything it will yield commits later, so the tail is an
   ordinary range from its start. The follower is still sent `Date.now()`, not a sentinel below every
   key, because `shouldForceBaseCopyForRetention` would read such a cursor as purged history and
   recopy an idle follower on every reconnect.

   A resumed copy tries the anchor as an exact entry first (`classifyResumeAnchor`) and resumes in
   append order when it names one; otherwise — a pre-#876 `Date.now()` cursor, an empty-log copy, a
   purged entry — it keeps the timestamp resume. Nothing is written to anchor a copy, so there is no
   new entry type.

   **Every failure degrades to the pre-#876 behaviour and says so**, rather than failing closed: an
   unreadable log, an unformable boundary, an unreadable anchor, or a resumed
   cursor that names no entry all fall back to the timestamp range with a `warn`/`error` line naming
   the database. Fail-closed was tried and withdrawn — it turned a storage hiccup into a reconnect
   loop copying nothing, and rejected the leader's own fallback cursors. The cursor
   version is therefore unchanged: what the anchor means is decided by _reading_ it
   (`classifyResumeAnchor`), not by negotiating a version.

   The sender's cursor and `SENDING_TIME_POSITION` are clamped to climb only, since append order is not
   key order.

   Not covered, and both needing the same durable-cursor work: a **relayed origin's log**, which is
   not anchored; and a **reconnect**, where the subscription resumes with `startTime` at the
   anchor key and `matchesSubscription` requires that `startTime` to be BELOW an entry's key — so an
   append-order range would be overruled by the subscription predicate anyway. The in-connection window
   is closed; carrying append-order mode across a reconnect needs it persisted in the cursor AND
   honoured by that predicate.

   **Unchanged v4 peers cannot safely apply historical full-copy puts (harper-pro#737).** A rejected duplicate/stale v4 put omits the primary write but still emits an audit previous-time placeholder. LMDB 3.5.6 substitutes its uninitialized/stale `previousTime`; a captured zero becomes float64 `2.0` (`40 00 00 00 00 00 00 00`). The legacy reader only recognizes a previous timestamp beginning with `0x42`, so it parses the remaining header at the wrong offset. Decoding `1100010a6f6c642d646174612d3100` as an ordered-binary key reproduces the reported `BigInt(1.2934670252442207e-231)` exception. The reverse copy is triggered during forward v4→v5 migration by v4's automatic leader selection; it is not a software downgrade. Updating the v5/core audit writer does not fix the shipped v4 writer.

   Current peers advertise `safeCopyAudit: 1`. The gate is on the capability alone, never on the peer's reported version: a peer that does not advertise `safeCopyAudit` — a v4 peer, or an older v5 build that predates this capability — gets the exact same treatment. A major-version probe was deliberately rejected here: the no-op-write hole this capability guards against lives in core's audit writer, not in anything version-specific, so a capability-less v5 peer is not provably safer than a v4 one. `legacyCopy.ts` verifies the existing baseline using batches of at most 256 primary keys and numeric assigned update timestamps. All table snapshots are pinned before the first verification RPC, so concurrent writes are left to replay. It verifies before sending any copy marker or advancing the cursor. Verification sends no historical puts, including peer-origin and third-party records. A missing/older row or an unverifiable schema produces an explicit error; historical restoration/downgrade into an unverified peer is unsupported — including a capability-less peer's own genuine first-time base copy, which this cannot distinguish from a reverse copy into an already-populated one. Tables without a numeric assigned update timestamp cannot establish this baseline. After successful verification, the existing completion transaction anchors incremental replay to the time before verification, preserving new writes. This does not repair generic no-op failures from retries or concurrent writes outside the base-copy producer.

   The failed-key memo is bounded per worker and rechecks the current local record first on reconnect, avoiding repeated full scans for a known gap. Operation probes have bounded waits and ignore late responses. Modern copy behavior, including the earlier clone-origin withholding rule, is unchanged. The legacy integration regression inspects raw LMDB audit entries after stopping the source: record-count success alone can conceal malformed duplicate audit entries.

8. **Blob durability watermark: holds on a local/transient gap, advances past a source-missing (ENOENT) one.** Records commit (== become visible) without waiting on their blobs; the persisted resume cursor instead tracks `lastDurableSequenceId`, which only advances to a committed sequence once that sequence's blobs (and all earlier ones) are durably saved (the `.finally` watermark advance + the `onCommit` clamp, both gated on `!hasBlobGap`). A blob save failure in `receiveBlobs` is classified. A **local/transient** fault (receiver `createWriteStream` ENOENT, disk full, mid-stream timeout) sets `hasBlobGap`, pinning the watermark so a reconnect re-streams and re-saves the blob — no silent loss (#368/#386). A **source-reported PERMANENT** failure — the sender's `sendBlobs` catch forwarded a `BLOB_CHUNK` `error` marker with `errorCode: 'ENOENT'` because the blob is gone at the origin (evicted/expired) — is unrecoverable: re-streaming reproduces it, so holding would wedge the connection forever. The receiver instead logs it loudly (`cluster_status.blobReplicationFailures` + a per-blob "advancing the resume cursor past it" error), advances, and leaves the diverged record for proactive blob backfill (#388). Classification is deliberately narrow (`isPermanentSourceBlobErrorCode` = ENOENT, or a forwarded `errorStatus` of 404/500 since harper#1425/#429): a transient sender fault (EIO, EMFILE, timeout, 503) or an older sender that doesn't forward `errorCode` stays unmarked, so it HOLDS like a local gap and a reconnect retries — never silently skipping a recoverable blob. The trigger is set on the destroy error via `markSourceBlobUnavailable`; the save `.catch` keys on `isUnrecoverableSourceBlobError`. See harper-pro#403.

   The held gap is **bounded, not open-ended** (harper-pro#683). `hasBlobGap` is a per-connection one-way latch — nothing in the connection's lifetime clears it; only a reconnect (fresh connection state, resume from the clamped cursor) re-streams the gapped blob and heals it. A latched connection keeps flowing frames and answering pings, so no byte/frame watchdog ever notices it; in the field a link sat latched for hours until an UNRELATED reconnect resumed a whole-table base copy (the latch also blocks `maybeFinishCopy`, so a copy that took even ONE transient fault never exits copy mode, and EVERY later reconnect resumes the copy). Three #683 mitigations: (1) the **blob-gap reconnect timer** (`createBlobGapReconnectTimer`, armed on latch, interval `replication.blobGapReconnectMs`, default `blobTimeout` = 900s — separately tunable since #699 so operators can shorten gap cycles without also shortening blob stream timeouts) forces the healing reconnect if none happens naturally; (2) the **per-position copy-cursor watermark** below; (3) the **sender retries a 503 blob read in place** (`BLOB_SEND_RETRY_BACKOFF`, only before any chunk is on the wire) before forwarding the error — the dominant 503 is the source's own PENDING placeholder from a concurrent receive (#481), a rolling population that self-heals within seconds, and under all-to-all copies every node is simultaneously source and receiver, so without the sender retry no large copy could complete gap-free and copies livelocked. 503 remains classified TRANSIENT at the receiver (holds the gap) — reclassifying it as permanent would trade a seconds-long contention blip for permanent divergence.

   **A held source-503 gap is bounded ACROSS reconnects, not just within one (harper-pro#432).** #683's timer bounds how long one socket holds, but every per-socket counter (the sender's in-place retries, `blobFailureCount`, the timer itself) restarts with the socket, so a source that answers 503 on every re-stream — the circular PENDING-stub wedge seen in the field — pinned the resume cursor forever. `NodeReplicationConnection.blobGapBudget` (`createBlobGapEscalationBudget`) lives on the connection object and survives socket replacement: the save `.catch` charges one cycle per socket generation (`blobGapGeneration`) for each held delivery, keyed `(source file id, table, record id)` — charged at the failed save rather than at the `BLOB_CHUNK` error frame because only a failed save proves the delivery holds the cursor (a peer can send error frames for file ids no record references), and keyed by record too because adjacent records can share one source file across distinct transfers. Once a delivery has been held for `replication.blobGapEscalationCycles` cycles (default 10) or `replication.blobGapEscalationMs` since its first hold (default 30 min; evaluated at each failed re-stream, so it is a floor rather than a deadline — with the stock 15-minute gap cycle it trips first, on the third failure) it is reclassified through `markSourceBlobUnavailable` and the existing advance-past branch skips it: an error line containing "blob-gap escalation budget exhausted", `cluster_status.blobReplicationFailures`, the local file unlinked (the backfill signal — reads of that record's blob then fail as gone rather than retryable-pending), cursor advances. Exhaustion is sticky until a successful save of that delivery — forgetting it would let two deliveries with offset phases leapfrog forever (A escalates and is forgotten while B holds; the next cycle re-streams A, which starts over while B escalates and is forgotten). Nothing evicts live progress, and every hold has a terminal bound even at capacity: at `BLOB_GAP_BUDGET_MAX_TRACKED` tracked deliveries the oldest exhausted entry the current socket has not re-held is dropped to make room (its record was already skipped past; a re-held one keeps its stickiness), and a hold that still cannot be tracked is charged against one shared capacity cohort with the same bounds, warned once per socket — the cohort conflates its members, which is why the cap is generous, but without it `BLOB_GAP_BUDGET_MAX_TRACKED + 1` persistent gaps could rotate forever with no gap-free generation. Any entry unseen for two _active_ socket generations (ones that held a delivery or settled a tracked one) is retired at socket start: the gap timer reconnects precisely to re-stream every held delivery, so silence means it healed, was skipped past (a permanent source failure also settles its entry), or was superseded by a new source file id; sockets that die before settling anything — a peer in a restart loop, a copy the watchdogs keep terminating — do not count, so an unstable link cannot reset a held delivery's clock. Only a source-reported 503 is budgeted; local save faults (disk, receive-stream timeout) and code-less older senders still hold indefinitely, and a process restart resets the budget. Setting a bound to `0` disables it; both `0` restores the pre-#432 unbounded hold. The keys are registered in core (`CONFIG_PARAMS`, config schema, validator) like `blobGapReconnectMs` — `getConfigValue` resolves registered names only. Operators: alert on the escalation line, then run `repair_blob_data` once the source recovers; note the sweep only sees the subscription connections of the worker thread it runs on (an operation dispatched to the main thread reports `noConnection`).

   **The copy cursor banks by walk position, not per connection (harper-pro#699).** #683's original snapshot (persist the last cursor staged at an instant with zero in-flight blobs) turned out to bank nothing in the field: a blob-dense copy never reaches a blob-quiescent instant, so under a sustained fault supply every watchdog cycle re-walked the same range — bounded, but zero net progress across days. `CopyCursorWatermark` replaces it: every copy frame gets a monotonic position at decode time, every copy-frame blob is tagged with its frame's position, and each committed frame's cursor is staged in order. A cursor is durable-eligible only when every blob tagged at-or-before its frame has settled without a transient failure; a transient failure sets a **barrier** at its own frame, so persistence clamps only from the first fault onward — everything walked before it persists (immediately, not on the cadence, since the watchdog may reconnect at any time) and the reconnect resumes at the gapped record. Pass identity (bumped per `COPY_START`) is validated at staging AND across every asynchronous persist edge (`passAtPersist` in `persistCopyCursor`), so a same-socket copy restart can never have a prior pass's late flush write a cursor claiming keys the new walk has not delivered. The barrier, like `hasBlobGap`, never heals within a connection; unrecoverable source-missing blobs settle un-gapped so the cursor still advances past them (#403). Live (non-copy) replication never touches the watermark.

   **A re-delivered identity-tie duplicate heals a dangling blob reference IN PLACE (harper-pro#699).** A record whose blob save failed transiently commits with a reference to a PENDING stub (#481) — and the re-delivery that carries the healing bytes is dropped by core's duplicate checks (copy-apply skip / audit-path resequencing tie), so before #699 the reference stayed dangling forever while the freshly saved blob (a new fileId) was swept as an orphan; #481's "the re-stream overwrites this stub" assumption never held. Now, for blob-carrying records inside the duplicate windows only (a copy frame, or a source still inside its leading-duplicate resume tail — live replication pays nothing), the receive path reads the stored entry BEFORE decode (`collectBlobRepairTargets`; doing it inside the decode's blob callback recurses into the stored value's own blob refs) and, on an exact identity tie (same version AND node — the same condition core's apply loop drops the duplicate on, so content is provably identical), streams the incoming bytes INTO the damaged existing fileId (core `repairBlobFile`: only when the file classifies missing/incomplete, only when no writer holds its `:blob` lock, and with the size header deferred so concurrent readers keep getting retryable not-yet-complete semantics during the overwrite). The record itself is still tie-skipped — no rewrite, no resequencing. Once a damaged target is selected, declining the repair or finding a descriptor-size mismatch fails that delivery and holds the cursor; saving fresh would leave the tie-skipped record pointing at damaged bytes. Repair failures settle through the same tracked-promise path as save failures, so the next cycle re-delivers and re-repairs.

9. **Receive-side blob streams carry a no-op `'error'` listener from creation**, so tearing down an orphaned stream cannot become a process-level `uncaughtException`. The invariant and its why are in `createBlobReceiveStream`'s docstring; pinned by `unitTests/replication/blobReplicationFailure.test.mjs` (harper-pro#409).

10. **The reconcile recovers two distinct wedge shapes, on two signals.** `subscriptionManager.reconcileWorkers` (main thread, every `RECONCILE_INTERVAL_MS`) is the independent safety net behind the per-connection recovery paths. (a) `findStaleNodeUrls` rebinds entries whose worker died. (b) `findWedgedNodeUrls` re-drives `connected:false` entries that wedged on a _live_ worker with no pending retry (`re-subscribe`; the #420/#424/#289 family). (c) `findStalledReceivingNodeUrls` re-drives `connected:true` entries stuck `RECEIVING_STATUS_RECEIVING` with no apply progress (the ping-alive base-copy wedge — keepalive pings keep the byte watchdog alive and the received-_version_ is frozen mid-copy, so neither (b) nor the byte watchdog sees it; harper-pro#453). Recovery for (c) is `forceReconnectToNode` (worker-side `connection.forceReconnect()`) **not** a re-subscribe — `getSubscriptionConnection` reuses a still-`connected` connection unchanged. The progress signal is `RECEIVED_TIME` read from the process-shared status buffer on the _main_ thread (`getReplicationSharedStatus`, as `cluster_status` does): it advances per applied copy record even while version is suppressed, so a slow-but-progressing copy keeps resetting the stall clock. Threshold (`RECEIVE_STALL_THRESHOLD_MS`, 15 min) is longer than byte-idle `COPY_TIMEOUT` (300s) but, at default config, about equal to the worker-local copy-progress watchdog's window (#454: `blobTimeout`, 900 s, plus a confirmation of up to 2×`PING_INTERVAL`); `receiveStallReconnectAt` gates re-drives to once-per-resumed-progress so a caught-up/cosmetically-`Receiving` connection is not churned.

11. **Directional self-record: `system` can replicate WITHOUT reforming a full mesh.** Historically a node wrote its own `hdb_nodes` row with `replicates: true`. Once `system` (which holds `hdb_nodes`) is itself replicated for discovery/config propagation, that blanket `true` propagates cluster-wide and every aggregation node opens a DIRECT subscription to every discovered node — a full mesh (a 1-core/30-roadside tree collapses into ~30 direct core↔roadside sockets). So the old guidance was "disable `system` replication to keep a tight topology," which also loses global users/roles/schema propagation. `computeSelfReplicates` (in `subscriptionManager.ts`) instead derives a DIRECTIONAL self-record (`{ sendsTo:[{target,database?}], receivesFrom:[{source,database?}] }`) from the node's own config routes, so the propagated record advertises exactly which neighbors this node sends to / receives from. The existing #498 gates (`shouldReplicateFromNode` receive-side; the send authority gate in `replicationConnection.ts`) then consult the discovered peer's advertised directions instead of a permissive boolean, so a discovered non-neighbor is never subscribed to and never sent to — `system` replicates (roles/users/schema reach everyone transitively) while user-database CONNECTIONS stay on the configured tree. Key properties:
    - **Opt-in.** The directional record is produced ONLY when the node has ≥1 directional route (a `replicates` OBJECT — `{sends/receives}` booleans or `{sendsTo/receivesFrom}` entries). A node with no routes, or only full-replication (`true`) / subscriptions-only routes, keeps `replicates: true`, so existing full-mesh and seed-based auto-mesh clusters are unaffected. An explicit "replicate nothing" directional route yields an EMPTY record, not `true`.
    - **Registry-set path.** `setNode`/`addNodeBack` (add_node/set_node) no longer force the self-record to `true`: `selfReplicatesForNodeWrite` PRESERVES an existing directional self-record and only derives from config routes (via `getConfiguredRoutes()`) / defaults to `true` when none exists yet. Caveat: `getConfiguredRoutes()` reads a main-thread-only module global, and an operation handler may run on a worker; so on a brand-new node whose main-thread `startOnMainThread`/`ensureThisNode` has not yet persisted the directional self-record, a worker-handled add_node falls back to `true` for this node's own row. That is no worse than the previous unconditional `true`, and it self-heals: `ensureThisNode`'s structural-diff rewrite replaces it with the directional record once startOnMainThread runs. (A node relying purely on config routes — the primary topology — writes its self-record from the main thread and is unaffected.) These handlers also no longer stamp a blanket `sends: true` on a directional PEER record (which would short-circuit the receive gate's allow-list to "feeds every database"). Consequence: an `add_node` with `sendsTo`/`receivesFrom` entries scoped by `database` now RESTRICTS to those databases (matching the config-route path); to replicate all databases minus a table, use a wildcard entry (`excludeTables`, no `database`).
    - **Leading-duplicate-skip and directional peers.** The multi-hop dedup exclusion (`SUBSCRIPTION_REQUEST` excluded list + `SUBSCRIPTION_UPDATE excludeNodes/includeNodes`) is OWNED by the main thread: `subscriptionManager.ts → computeExclusionOrigins` decides, per database, which origins a relay may be told to omit, and the http workers only apply the set (carried on the `subscribe-to-node` payload, refreshed by `update-exclusion-origins` messages on `hdb_nodes` changes). An origin qualifies only when the EFFECTIVE local receive decision accepts a direct subscription (`shouldReplicateFromNode`, config-route precedence per harper-pro#498), its row's advertised intent covers this subscriber+database with no table exclusions (`qualifiesForMultiHopExclusion`, `knownNodes.ts`, the advertised half only), and the local `receivesFrom` filter drops nothing from it (`getExcludedTablesForRouteEntries`). The workers must not decide from `hdb_nodes` rows themselves: the advertised `sendsTo` is not the effective receive decision (a config route can disable or table-filter a direct path the row advertises), and with no set supplied a session excludes nothing beyond this node's own log. History: directional peers were previously never excluded (the qualifier tested only `replicates === true || replicates?.sends`), so every subscriber received a directional origin's writes once per mesh member; each redundant delivery persisted a same-version audit entry (harper#2485; deterministic per delivery, no double-apply), making restart replay O(peers²), observed wedging a 16-node mesh's database at 350 w/s. Exclusion remains the data-loss-prone direction (excluding an origin without a real full-coverage direct path drops records, cf. the #370/#399 leading-dup-skip family), which is why the decision requires the effective config only the main thread has.
    - **Refresh on config change.** `ensureThisNode` compares `replicates` structurally (not just url/shard), so a `deploy_component` reload picks up route/topology changes and rewrites the row.
    - **Decode-recovery preserves direction.** `mergeReconstructedNode` (in `knownNodes.ts`) keeps a peer's last-known directional `replicates` when its row transiently fails to decode, instead of clobbering it to the reconstruct's `true` — so a decode miss doesn't briefly widen a constrained topology back to a mesh.
    - **Boundaries.** (a) Central visibility of every far leaf is NOT guaranteed: the `hdb_nodes` registry relay to a sink differs from data relay, so e.g. core often does not list a roadside leaf. This does not cause a connection either way; it is an accepted tradeoff. (b) On-demand residency/retrieval connections (`getRetrievalConnectionByName`, for sharded or invalidated-cache reads) are governed by data residency, not subscription directionality, and are a separate mechanism from the subscription topology this record constrains. (c) A directional edge added dynamically via `add_node` to a NON-config peer is not durably self-advertised across a `deploy_component` reload (the self-record is derived from config routes) — config routes are the authoritative source for a node's own directionality.

12. **Outbound-subscription reconnect recovery is layered (belt-and-suspenders), and every layer must self-heal a never-`open`ed connection.** A `(peer, db)` subscription that drops or never connects must always end up with _some_ pending recovery; three independent drivers cover this: (a) the close handler / `forceReconnect` re-drive `connect()` through `scheduleReconnect()` with backoff; (b) the receive watchdog calls `forceReconnect()` on an open-but-idle socket that never emits `'close'` — and, because that byte watchdog is suspended while the socket is paused for back-pressure (`bytesRead` frozen), a **pause-stall watchdog** companion (`createPauseStallWatchdog`, item 6) covers the paused window by watching consumer progress instead, so a leg that dies mid-pause still reconnects; (c) the main-thread reconcile (`findWedgedNodeUrls` → `reconcileWorkers`) re-drives an entry that has been not-`connected:true` past `WEDGE_RECONCILE_THRESHOLD_MS`. The trap (harper-pro#466): `connect()` `await`s `createWebSocket()`, which can **reject before any socket/listener exists** (no valid replication cert yet, or `SNICallback.initialize()` failing while a freshly-restarted peer rebuilds its TLS secure contexts). Because the re-drive is `setTimeout(() => this.connect())` with no `.catch()`, that rejection escaped as an unhandled rejection and the only pending retry vanished — so `connect()` now catches it and routes back through `scheduleReconnect()` (`reconnectScheduled` stays true with a fresh timer; it is cleared only on the _success_ path after `this.socket` is assigned). Two subtleties the reconcile backstop must respect: a **never-`open`ed** entry has `connected` still `undefined` (not `false`) and no `disconnectedAt` (only `disconnectedFromNode` stamps that), so the wedge predicate keys on `connected !== true` with `downSince = disconnectedAt ?? createdAt` (createdAt stamped at entry creation); and re-posting `subscribe-to-node` only re-`subscribe()`s a still-`isReusableConnection` cached connection — it does **not** reconnect it — so the reconcile sets `forceReconnect:true`, applied by `subscribeToNode` **only to a reused connection** (a freshly-created one already called `connect()`), and only to a database that independently passes the wedge predicate (the URL is flagged because _some_ db is wedged; a healthy or grace-period sibling db must be left alone). See harper-pro#420/#424/#289/#233/#466.

13. **A connection's local subscription may be an unresolved placeholder — never read `send`/`auditStore`/`dbisDB` off it.** A replication connection for a database is set up independently of `Replicator.subscribe()`, which registers that database's `IterableEventQueue` in `databaseSubscriptions` when the first of its tables is set up on this thread. Whichever loses the race, the connection is handed the placeholder Promise from `createPendingDatabaseSubscription` instead. Both use sites got this wrong (harper-pro#622): the receive path called `.send()` on it (a `<x>.send is not a function` per inbound message, every record in it dropped — 329k errors / 500MB of `hdb.log` in 8 minutes on a 12-node cluster), and `sendSubscriptionRequestUpdate` read `auditStore`/`dbisDB` off it, so `nodeId` was `undefined`, no `seq` cursor resolved, `startTime` fell back to `1` and the node **requested a full copy of every database on every restart while a current cursor sat on disk**. The two fixes are asymmetric because their requirements are: (a) the record path genuinely needs the resolved queue, so it waits (`awaitPendingSubscription`, bounded by `SUBSCRIPTION_RESOLVE_TIMEOUT` — nothing else watches a wedged `messageProcessing` chain, since the receive watchdog is reset by the very frames not being processed — and pausing socket intake for the wait, because blocking that chain does **not** stop `ws.on('message')` from appending closures that each retain a whole inbound frame, so a peer mid-copy would OOM the worker before the timeout fired; `PAUSE_STALL_THRESHOLD_MS` is floored above the timeout so the paused-liveness watchdog can't pre-empt the wait); (b) the handshake must **not** wait — an empty node bootstrapping a database it does not have locally would deadlock (the peer only sends `DB_SCHEMA` in response to a subscription request, and that schema is what creates the tables that resolve the placeholder) — so `resolveDatabaseStores` reads the stores off a local table instead (`table.auditStore` / `table.dbisDB`), both being per-database with the subscription queue only a carrier. Empty stores then mean what `startTime === 1` always assumed: no local tables at all, i.e. a genuine bootstrap. Compare `readDbisCursorSync` (#476/#484) — same "`undefined` masquerades as no resume cursor → spurious full copy" failure, different source of the `undefined`.

14. **Transport liveness does not prove subscription setup completed.** On the sender, both the dynamic `hdb_nodes` authorization subscription and the database's internal subscription placeholder must resolve before `DB_SCHEMA` is sent and the replay loop starts. A never-settling promise used to leave that `(peer, db)` socket ping-alive forever with no application frames, no received-version/time, and no cursor movement (harper-pro#642). Both sender gates are now bounded by `SUBSCRIPTION_RESOLVE_TIMEOUT`; expiry logs the exact gate and closes transiently so the subscriber retries from its last durable cursor. This deliberately also retries a peer/database mismatch whose placeholder can never resolve, matching the receive-path bound: the state is indistinguishable from a registration failure and may become valid after deployment. Independently, peers advertise support for a correlated setup acknowledgement and their effective two-gate setup budget in `NODE_NAME`; the outbound receiver then attaches a request id to each non-empty `SUBSCRIPTION_REQUEST` and arms a one-shot **subscription-setup watchdog** for the advertised budget, capped at the larger of four times its local window or ten minutes so a peer cannot disable the receiver's recovery net. A peer configured beyond that cap may therefore see periodic recovery reconnects instead of a suppressed watchdog. The post-gate `DB_SCHEMA` retires the watchdog only when it echoes that exact id. This correlation is required because the `system` handshake sends unsolicited schemas before the subscription request is processed, and a superseded replay can still have frames in flight. A receiver disables this independent watchdog when its sending peer does not advertise the capability, preserving wire compatibility without treating an unsolicited schema as an acknowledgement. In a mixed-version pair the setup-stall fix therefore depends on the **sender** being upgraded so its gates are bounded; upgrading only the receiver cannot safely distinguish an old sender's handshake schema from a setup response. Expiry calls `forceReconnect()` and includes the W1 truth snapshot, because the socket truth is legitimately connected — this is application-progress semantics, not a connection-truth failure. The watchdog is suspended during intentional socket back-pressure, cancelled on close/unsubscribe, and rearmed by a superseding request. A bounded wait that gives up must also **retire** the placeholder it waited on: it is registered in `dbSubscriptions` and only `Replicator.subscribe()` resolves it, so a permanently-unresolvable one would otherwise collect a fresh waiter (retaining a whole connection's setup state) on every peer retry. Retiring settles it, unregisters it, and marks it — the mark is load-bearing because connections seed every reconnect from the subscription they were constructed with and siblings for the same database share the object, so every consumer must treat a retired placeholder as absent and re-derive through `subscriptionForConnection()`, which also never registers a placeholder over a registration that landed in the meantime. Crucially, setup acknowledgement never advances the durable cursor: a zero receive timestamp is ambiguous for a healthy caught-up peer, and `SEQUENCE_ID_UPDATE` is cursor-mutating rather than a harmless ACK.

15. **Watchdog fires must survive three ownership checks: pause state, socket identity, and transport evidence.** (a) The copy-progress watchdog is stopped by `addPauseReason()` because a back-pressure pause silences copy frames BY DESIGN, but the stop is only half the invariant: any post-pause `reset()` re-arms it into the paused window, and the commit-backlog pause trips mid-frame with the same frame's `noteCopyProgress()` still to run. So `noteCopyProgress` resets only when `pauseReasons === 0` (the same guard `resetPingTimer` carries from the #466 review), and `removePauseReason` re-arms on resume. A violated guard reads as "no base-copy progress for `blobTimeout`" fired against a healthy copy whose apply loop is demonstrably committing (database-size growing while the line claims silence; observed for 17 hours on a migration cluster). (b) Watchdogs live per `replicateOverWS` instance but fire onto the SHARED `NodeReplicationConnection`, so supersession must retire the whole instance rather than only silencing its watchdogs. The invariant is **at most one live session per connection, and it is retired at the point its socket stops being the connection's socket** — enforced in `NodeReplicationConnection.retireSession()`, which runs the superseded session's `retire()` (the close listener's full teardown, extracted as the idempotent `retireInstance`: keepalive, sweep and back-pressure intervals, every watchdog and the blob-gap reconnect timer, subscriptions, pending requests, in-flight blob aborts). Every supersession path calls it: `connect()` immediately after the new socket is installed (covering any replacement, including future ones), and `forceReconnect()` up front so a wedged-but-open socket's keepalive stops refreshing shared liveness right away instead of at the end of the backoff window — both because the old socket's close may arrive late or never, which is precisely the wedge these paths exist to recover. A session created by an `open` that raced a replacement is retired on the spot. As a backstop, `firingFromSupersededInstance` checks `options.connection.socket === ws` before any fire handler acts (mirroring the close handler's identity guard), so an instance that leaked past explicit retirement runs the same full retirement itself and stands down instead of acting. Without these, a leaked instance fires up to `blobTimeout` after its leg died and kills the CURRENT healthy leg; in the field this produced one kill per churn cycle, phase-locked, with the misleading 900s claim landing on a 300s grid. Deterministic repros: `copyProgressBackpressureFalseFire.test.mjs` and `watchdogSupersededInstanceFire.test.mjs`, driven by the one-shot `HARPER_TEST_COPY_COMMIT_DELAY_ONCE_DB` and `HARPER_TEST_LEAK_CONNECTION_AFTER_COPY_START_DB` hooks. (c) A third ownership check is transport evidence: the copy-progress watchdog fires only when received peer bytes moved during the copy-silent window AND kept moving through a transport-scale confirmation (2× `pingInterval`) — its #453 signature is ping-alive-but-frame-dead, and a live peer proves itself with a fresh pong within a ping cycle. The confirmation exists because one window of movement is not proof: bytes buffered behind a receive pause or a suspended peer's kernel send buffer land moments after a re-arm — observed as a partial-frame tail draining right after a back-pressure resume — and that residue always empties within milliseconds, while it cannot recur a ping cycle later. Sizing the confirmation from the ping cadence rather than `blobTimeout` keeps the configured value the recovery bound (detection stays 1–2× `blobTimeout` + ≤2× `pingInterval`, not 2× `blobTimeout`). Windows dark on bytes — a starved or suspended peer, seen as a 4.4s event-loop stall on a nightly CI runner firing the 2026-08-29 false positive — are transport-level silence and belong to the byte watchdog's `COPY_TIMEOUT` budget (and the keepalive idle terminate), not to `blobTimeout`; the watchdog re-arms and stands down, and the copy resumes on the same connection when the peer wakes. An unobservable or throwing byte sampler counts as no evidence (stand down, one debug line) — never as licence to fire. Deterministic repro: `copyProgressSourceStallFalseFire.test.mjs` (SIGSTOP the source past `blobTimeout`, then past `COPY_TIMEOUT` to prove the byte watchdog takes ownership). Note the production defaults already order these budgets (`COPY_TIMEOUT` 300s < `blobTimeout` 900s), so the gate mostly matters where `blobTimeout` is configured below `copyTimeout` and as the stated invariant; `findStalledReceivingNodeUrls` (item 10) stays the 15-minute reconcile-level net beside both. Open (issue #697): what creates silent-from-birth surplus legs for the same `(db, peer)` in the first place; that needs sender-side evidence.

16. **A bulk copy must preserve each row's true origin `nodeId` in the encoded audit entry.** The mesh is bidirectional, and a node with no resume cursor for a peer requests a full copy from it (item 13 / #426) — so when an empty node B joins, the established source A full-copies FROM B and receives its own rows echoed back. Conflict resolution (`core/resources/Table.ts → precedesExistingVersion`) skips an identity tie (same version AND same origin node) but breaks a same-version/different-node tie **alphabetically by node name**. The copy sender used to stamp its OWN id (`getThisNodeId` = 0) on every copied row, so the echo arrived attributed to B: the tie fell to the name comparison, and on the name-smaller node every echoed row WON — the source silently re-applied its entire own dataset, re-minting every blob from the peer's stream and unlinking its original files (identical bytes, so invisible — until a crash mid-echo left committed records referencing permanent PENDING stubs with the originals gone, and later re-deliveries identity-tie-skipped so the stub never healed: the QA-692 nightly failure, where the never-killed source failed its own sanity gate). The copy loop now encodes `entry.nodeId ?? getThisNodeId(...)` (origin ids are in the sender's local id space — exactly what the wire carries and `NODE_NAME_TO_ID_MAP` resolves), making the echo an identity tie the receiver skips. The audit-like record carries that origin id so `sendAuditRecord` exports its mapping before the frame; the sender id is passed separately for subscription matching, preserving `subscribedNodeIds` filtering. The copy-origin match can also reach `Table.ts`'s end_txn seq bookkeeping, but that write is dormant today because replication end_txn events carry no timestamp. The fix is not retroactive: rows persisted by a pre-fix copy retain the relay's id, so a post-upgrade full copy from the true origin can still re-apply them on the name-losing side until the rows are rewritten. Deterministic repro: `fullCopyEchoSourceIntegrity.test.mjs` snapshots the source before the natural join and requires that its blob-store file set remains unchanged.

17. **Resolver output is never replicated.** No durable form of a record — copy payloads, audit entries, residency partials — carries a value under a `@computed`/`@relationship` name; core's durable projection enforces this at `recordUpdater` and on receiver materialization (HarperFast/harper#2359, harper#2368), the copy sender projects each re-encoded row to stored fields, and the residency-partial sender skips resolver-owned indexed names outright. A receiver recomputes computed values from the stored inputs it has; a non-resident peer that lacks those inputs does not index the resolved attribute. Residency-changing patches reconstruct the record at the audit timestamp (`getResidencyProjectionRecord`) so peers do not receive bodyless invalidations. Regressions: `unitTests/replication/copyBlobTransferMetadata.test.mjs` and `integrationTests/cluster/computedFullCopy.test.mjs`.

18. **A replication frame carries two clocks, and the RocksDB receiver adopts them separately (harper-pro#790, harper#2412 stage 0b).** The frame's leading float64 is the origin's **transaction-log key** (`txnLogKey`) — the batch key its entries occupy in the origin's own transaction log, which is what `sendAuditRecord` groups a transaction by and what a peer resumes from. The forwarded audit-entry bytes carry the record's own **version**, which the source may have set to something else entirely (a cache fill reports the source's `lastModified`, core #2065). The two coincide for every ordinary write, which is why conflating them stayed invisible: the receiver used to skip the frame header (`decoder.position = 8`) and put the entry's version on the apply event as its transaction `timestamp`, so a peer keyed the origin's write in its copy of the _origin's_ log at the source's clock. Leaf state looked right; a third node resuming through that peer read cursors in a domain the relay's log no longer used, and the receive-path resume cursor (`maxBatchTxnLogKey` → `endTxn.localTime`) and the `RECEIVED_VERSION_POSITION` watermark were maxima over record versions rather than log positions. Now the receiver reads the frame's transaction-log key once, validates it (`isValidFrameTxnLogKey`: finite, `> 0`, `<= 8.64e15` — a corrupt or hostile value would otherwise reach `setTimestamp`, the durable cursor and the status watermark, and every reconnect would wedge on the same frame; an invalid frame holds and reconnects, leaving every cursor untouched), and on RocksDB puts it on the compatibility apply event as `timestamp` while `version` carries the origin's record version for core to store per write. A full-copy row recovers the same key from core's audit-head reference when its stored version differs, so `event.isCopyApply` can compare the log key with `copyStartTime` and leave every write in the subsequent replay auditable. Deprecated LMDB keeps its existing record-version transaction timestamp and grouping. No on-disk or node-to-node frame identifier changes. Rolling upgrades: neither direction breaks, but the guarantee is the RECEIVER's to hold. An old sender already writes the transaction-log key into that header, so a new receiver reads the right value from an old peer. An old receiver ignores the header and keeps filing an origin's writes under the source clock, exactly as it does today: a new sender makes nothing worse, and fixes nothing on that hop, so a relay still on the old build keeps the harper-pro#790 divergence until it is upgraded. Upgrade receivers and relays before relying on the invariant. Historical entries a pre-upgrade peer keyed at a fill's version cannot cause a skip once it is upgraded, because a source version is bounded by the later local commit key — a cursor carried across the upgrade re-delivers rather than skips; the miskeyed history itself is only corrected by a re-clone. Sites that legitimately stay on the record version: `isDurableIdentityTie` and `collectBlobRepairTargets`; `event.isCopyApply` stays in the log-key domain with `copyStartTime`. Deterministic repro: `dualClockOriginTxnLogKey.test.mjs` (O → R → T, a backdated fill, an unclean T restart and a resume through the relay).

The full-copy audit-head lookup is best-effort across retention. If the referenced head has already
expired, the sender uses the bounded record clock instead. That row is a pre-`copyStartTime` snapshot,
not a replayed transaction: it creates no audit entry and its frame key is never stored as a resume
position. This keeps bootstrap available without conflating clocks in the subsequent audit replay.

19. **Blob codec preservation is advertisement-gated, announced before the record, and verified at both ends (harper#2443).** A deflate-stored blob (core's opt-in `storage.blobs.compression`) is streamed as its RAW stored body instead of being inflated on send and (potentially) recompressed on receive — but only to a peer whose `NODE_NAME` capabilities object advertised `acceptBlobCodecs: ['deflate']` (`HARPER_REPLICATION_ACCEPT_BLOB_CODECS=0` is the receiver-side kill switch; an old peer advertises nothing and gets today's inflated stream). Three non-obvious constraints shape the mechanism. (a) _The codec must reach the receiver before the record_: records go on the wire as raw stored audit bytes (never re-encoded per peer), and the receiver stamps the blob file's header the moment record decode starts the save — so `sendBlobs` sends a zero-length announcement `BLOB_CHUNK` (`{fileId, transferId, size, codec}`) in its synchronous prefix, inside the same synchronous block that is building the record frame, guaranteeing wire order; the receiver's existing chunks-before-record handling pins `stream.codec` from it. (b) _The sender decides from local file truth, cheaply_: the `storedCodec` hint core stamps into the stored blob-ref options prefilters (the uncompressed majority pays zero extra I/O), and `openStoredBlobBody` then confirms against the actual header with a sync 8-byte sniff + write-lock probe before committing — a relayed record can outlive the storage form it was written with, so the hint alone is never trusted, by sender or receiver; the stream re-reads the header on its own descriptor when it starts, and a file replaced in between (a repair publish) fails the transfer with a transient 503 — the receiver holds the gap and re-decides on reconnect rather than advancing past it. Once announced, the transfer must deliver raw bytes or a terminal error frame — never silently fall back to inflated bytes, which the receiver would store under a deflate header as garbage. (c) _Both ends verify by concurrent inflate_: the sender's stored-body stream fails (500, classified permanent → cursor advances, matching today's torn-blob semantics) if the body does not inflate to exactly the header size, and the receiver's `createBlobFromStoredBody` write rejects on the same condition, so a torn or forged body can neither ship nor publish. The receiver binds a codec only alongside a valid size — `Number.isSafeInteger(size) && size >= 0`, not a bare `typeof === 'number'` — because the inflate output cap is the only bound on a raw peer body, and a `NaN`/`Infinity` size would make `inflatedLength > expectedSize` never true and let a compression bomb expand unbounded into the repair temp file; `createRepairInflater` refuses such a size outright as a second line of defense. The in-place repair path (#699) keeps its uncompressed write contract — a codec-preserved re-delivery feeding `repairBlobFile` is inflated locally first, through `createRepairInflater` (a `pipeline`, so a declined repair's destroy settles instead of escaping as an unhandled inflater error, with output capped at the expected size) — and its damage classification is deflate-aware: a compressed header records the uncompressed length, so a body torn by an unclean mid-write shutdown looks whole to a length check. Core's `blobFileMissingOrIncompleteAsync` (the unlocked prefilter, also the durable identity-tie verifier) inflates to classify and records the damaged file's identity; core's locked sync recheck confirms that identity instead of inflating on the event loop, so a repair candidate must be probed async first or the recheck declines. Without that, compression would make the repair decline exactly the damage it exists to heal. Regressions: `blobCodecPreservation.test.mjs` (cluster), `blobCodecCapability.test.mjs` (unit), and core's `blobCompression.test.js`.

20. **A replicated transaction has one origin and one connection, and a frame is not a transaction.** A sender frame holds every entry at one `txnLogKey` across the sender's logs (every subscriber sends an exclusion list, so the merged all-logs walk is the normal send path), so it can carry several origins' transactions; within a frame the receiver starts a new transaction (`beginTxn`) when the origin changes, because RocksDB binds a transaction to one origin's log. The resume cursor still advances only at the frame's `end_txn`, after every segment commits, and a crash between segments replays the whole frame, whose applied records core drops as version-and-origin ties; splitting on the sender instead would put two frames at one key, and the `exclusiveStart` resume would skip the second after a crash between them. Every event this connection queues carries `txnStream` so core's apply loop keeps its transaction apart from other connections' (see core `resources/DESIGN.md`), and a frame that ends without its `end_txn` (socket closed at a yield, or a thrown error) is followed by `abort_txn`. A record whose origin id is not in the peer's id map closes the connection instead of being applied. A transaction that fails holds the connection's cursor: core records no sequence id past it and calls the frame's `onFailure`, which reconnects to replay it up to `replication.failedFrameReplays` times (default 5) and then moves past it with an error, so a failure that recurs on every delivery cannot stall the peer. A blob-drain `end_txn` that lands while a frame is open is deferred to after the frame's own `end_txn`, which would otherwise be closed early.

21. **Echoed delete runs already on disk are repaired offline, never on the send path (harper-pro#826).** Before harper#2761, a mesh could echo one replicated delete into millions of copies under its origin log key. The sender frames every consecutive entry of one timestamp as one message and checks `replication_maxPayload` only at flush, so such a run closes the leg on every reconnect. `repairDeleteEchoRuns.ts` (CLI `dist/bin/repairDeleteEchoRuns.js`, run with Harper stopped) drops a delete only when its replicated bytes (everything after the local prelude) equal a delete of the same record kept earlier in the same one-timestamp run, with no other entry for that record in between; everything else is copied verbatim. The run carries into the next file when the previous one ends on a closed transaction, as the sender frames it; after a transaction split across files (older writers) the next file's first entry is always kept, so that transaction still carries its last flag. A rewrite must keep what readers key on: the last-entry flag moves to the transaction's last kept entry; `txn.state` is remapped, and rewound to the file header while that file is swapped, because rewinding only re-applies flushed writes; a rewritten newest file gets a header-only successor stamped with the store's latest timestamp. rocksdb-js starts a query in the newest file whose header timestamp is below the start, so an older stamp skips the earlier files; the new sequence also means no stale derived-index `coverage` position can equal the tail. Anything whose byte positions the tool does not understand is refused: a non-zero append boundary, an unknown side file, an unclosed newest file, a torn tail. Apply and restore hold RocksDB's own `LOCK` for their whole run by opening the database writable with its transaction logs pointed at an empty directory: a store over the real logs would purge files when it closes, and every handle in the process shares it, so the reader read-back runs in a child process (a read-only open takes no lock). Started as root, the CLI first becomes the database's owner, so every file written, RocksDB's own included, belongs to that user and nothing is re-owned by path. `/proc/locks` and `hdb.pid` cannot see a Harper in another pid namespace, which is why the tool takes the lock rather than looking for it. A manifest in state `preparing` is written before anything else and precedes every store mutation, so a backup still in that state is removed, while one with no manifest is not the tool's and is refused; a store Harper ran on after an unfinished repair is consistent, and deleting its backup keeps it. A one-timestamp run too large to compare within the memory budget refuses its file rather than being partly deduplicated, which could leave it above the cap. Covered by `unitTests/replication/repairDeleteEchoRuns.test.mjs` and `integrationTests/cluster/deleteEchoRun.test.mjs`.

22. **A forwarded operation always settles on the sender, and never carries the sender's user.** `sendOperationToNode` (`replicator.ts`) resolves with the peer's answer, or rejects on a socket error, on the connection closing before an answer, or at `options.timeoutMs` — one timer, running from before the connection opens. It settles through the session's promise with `then`, not `resolve(promise)`, because adopting that promise left its own deadline dead once the socket opened. `replicateOperation` passed no deadline at all, so a peer that stopped answering a replicated `deploy_component` held the origin's operation, its deployment row and its restart until the peer restarted; it now forwards the caller's `timeoutMs` (core passes one for deploys — see core `components/DESIGN.md`, "An origin waits for a peer's deploy answer"). A rejection says the operation's outcome on that node is unknown, because nothing cancels it there. Every failed peer is logged at warn with only the operation's name, the node and the reason — never the body, whose secrets a redaction list may not know yet — and on the peer, `answerOperation` warns when an answer is ready after its connection closed, the only trace of a deploy that finished after the origin stopped waiting. The operation that crosses the wire has no `hdb_user`: the receiver's `server.operation()` replaces it with the connection's node identity, so the sender's user record, 30-day `refresh_token` included, was only ever logged at debug on both ends. `redactOperationForLog` still masks it for senders that predate the strip, and covers every field core's operation log drops (`UNLOGGABLE_OPERATION_FIELDS`), held there by `unitTests/replication/logRedaction.test.mjs`.

23. **Config-route reload publishes atomically.** `startOnMainThread` is re-entered on component reload while the previous keyed `hdb_nodes` watcher can still deliver events. The module-level `routes` array is also the authoritative main-thread input for leader inference and `configRouteReplicates`. Clearing it before asynchronous route preparation exposed a false "no configured leader/route" state: an existing subscription could retain or lose the wrong `isLeader` value, and a directional receive gate could temporarily fall back to the peer's differently encoded registry record. Route preparation now builds a local list and replaces the shared array contents in one `splice`, preserving the reference returned by `getConfiguredRoutes()`; tentative route-node updates run only after that commit. Effective leadership is recomputed before the existing-entry fast path, with explicit persisted `false` overriding configured inference.

24. **A peer's `hdb_nodes` key is the name it reports, not the address an operator used.** `add_node` stores the row under the `add_node_back` response's `nodeName` (the peer's `getThisNodeName()`), so `remove_node`/`update_node` resolve the caller's hostname through `setNode.ts → findExistingNodeRecord`: the exact key, else the single peer row whose stored `url` equals the derived one. More than one url match is refused (only `name` is a key, so a row stored under a typed address when the peer never answered can share a url with the live one), and `remove_node` (unlike `update_node`) never resolves an address to this node's own row: removing it takes this node out of replication with every peer, so only the exact name does that. An exact key always wins, even when other rows share its url — refusing it would also refuse their exact names and leave no way to remove either — so `remove_node` names those rows in its result instead. The full-replication `remove_node_back` must carry that key: the peer's `removeNodeBackFromTable` accepts only its authenticated caller's name or its own. `remove_node` deletes locally before contacting the peer (#752), so a reciprocal the peer did not confirm within its deadline is reported in the 200 result, not thrown. Pinned by `removeNodeFromTable.test.mjs` and `integrationTests/cluster/removeNodeAlias.test.mjs`.

25. **A `replicate: false` table never leaves its node, on any path (harper-pro#883).** The declaration that counts is the **sender's own** `Table.replicate` (read through the live database map, so a redeclared table is seen at once) via `tableReplicates` in `replicatedDatabases.ts`; before this, the only outbound table filter was the peer's `SUBSCRIPTION_REQUEST`, so a peer that had not declared the table — a fresh clone or `add_node` join, or a stale schema — asked for everything and got it. What never leaves: the table's **records, blobs, and definition on the replication socket**. Outside that boundary by design: the authenticated operations API (`describe_*`) and application packaging (`cloneApplications`), because the epic's model declares a plugin's node-local schema on every node. Enforcement points: `tableToTableEntry` (the one outbound table gate — audit path, copy loop, copy-resume validation — which also carries the route `excludeTables`, so a copied row's blobs are never opened for a table whose rows would then be skipped; the copy walk re-checks per row and stops the table on a flip); `GET_RECORD` answers an error-shaped `GET_RECORD_RESPONSE` before `TABLE_FIXED_STRUCTURE`, the store read or any blob, with one generic wording for an unknown and a non-replicated table; `tableDefinitionsForPeer` omits the table from `NODE_NAME[3]` and `DB_SCHEMA`; cloneNode's `cloneSchemas` skips it (and a database with no replicated table) and `getLastUpdatedRecord` excludes it from the sync target. Receive side, defense in depth for a sender that predates this: the record is dropped like a route-excluded one (`recordReplicationHole`, blob chunks discarded by the same path), and `ensureTableIfChanged` never merges a peer's definition into a local `replicate: false` table.

**Schema handshake: omit, not preserve.** The frame carries only `{table, schemaDefined, attributes[{name,type,isPrimaryKey}]}` and the receiver materializes it with `ensureTable({origin:'cluster'})`, so "preserve" would create a replicated-by-default twin that the peer then subscribes to and replicates its own writes out of; carrying the flag would be a shape change pre-fix receivers ignore, while omission is correct on every receiver version. `NODE_NAME[3]` has no reader at all. A twin created by a pre-fix join is left in place (deleting could destroy local data); it shows in `describe_table` without `replicate: false`.

**What a live declaration change can and cannot do.** Core since harper#2903 assigns an explicit non-cluster `replicate` declaration to the live `Table.replicate` in `declareTable`, including when it reuses an existing class. Redeploying an existing table with `@table(replicate: false)` therefore takes effect on the first redeploy restart; the former two-restart limitation is closed. Cluster-origin declarations cannot override that local choice. The join regression covers both a table created local and a populated replicated table redeployed as local, awaiting the deployment's HTTP-worker rollout and both table routes before joining the peer.

The audit send path and copy walk re-read the live declaration to observe changes and drop/recreate replacements. The copy check sits after the pacer's yield so no await separates it from the encode that opens the row's blobs (one property read, measured at ~6 ns against ~13 ns for one of that row's own allocations; sustained audit-stream throughput is not measured). The receive-side blocked set is discarded on `onUpdatedTable` rather than snapshotted for the life of the socket.

A table that leaves scope mid-walk still gets `COPY_COMPLETE` for the pass, so re-enabling it later needs a resync — the copy cursor advanced past its uncopied rows. A database in replication scope whose every table is non-replicating subscribes on neither end, so it gets no clone sync target (`hasReplicatedTable`) and no required socket — a resume marker written before that filtering re-derives its targets rather than waiting on one; it still opens no (peer, db) socket, so keep such a database out of `replication.databases` rather than relying on that.

Regressions: `unitTests/replication/replicateFalseSendPaths.test.mjs` (frames), `integrationTests/cluster/replicateFalseFullCopy.test.mjs` (join), `integrationTests/cloneNode/cloneNonReplicatedTable.test.mjs` (clone).

26. **Per-origin resume cursors (harper-pro#989, W4 harper-pro#434 scope item 1).** An origin a subscription neither lists nor excludes — a node removed with `remove_node`, or one reaching the subscriber only by relay — used to start at 0 on every resubscribe, so each restart resent a removed node's whole retained log, and every node added later pulled it too. Now:
    - **Receiver records.** Each committed non-copy frame's origins go into the connection's `[seq, peer]` row as `nodes[].originLogKey` = the highest frame key applied, held under the durable watermark's blob rule (`takeDurableOriginCursors`; core merges them from the `end_txn`'s `originCursors`, see core `resources/DESIGN.md`). A cursor is per peer, never borrowed from another peer's row: another subscription can cover a different table scope.
    - **Receiver sends** `buildOriginCursorVector` on `SUBSCRIPTION_REQUEST[4]`, and fresh cursors with an `includeNodes` update. A removed origin (its `hdb_nodes` row deleted, which leaves a tombstone `probeNodeRow` reads as `deleted`) was excluded on every relay while it was a direct peer, so it is seeded from its own connection's row: its own-origin cursor, or `seqId` on a row written before this change. The seeded cursor assumes that direct subscription covered every table the relay now supplies; it is the advertised coverage `computeExclusionOrigins` relied on, not a recorded one, so a narrower effective send scope would let the seed suppress relayed rows older than the cursor minus the overlap (accepted on #989 to avoid a full replay of every removed origin). A current member is never seeded that way — unlisted and unexcluded means partial coverage, and its direct cursor does not cover the tables it relays.
    - **Sender applies** `ORIGIN_CURSOR_OVERLAP_MS` (60 s) below each cursor, for unlisted, unexcluded origins only, in three places: the incremental range's `startByLog`, `matchesSubscriptionPosition`, and the `includeNodes` path (the floor goes into the live range's `startByLog` map before `addLog`, core's `addLog` re-reads log membership, and the update wakes an idle sender). It never goes into the copy's boundary range: `resumeAfterExactStart` treats every `startByLog` log as an exact start. An origin with no cursor still starts at 0. **The overlap is not a proven bound** — a transaction that took its key and committed more than 60 s later is skipped on resume. A listed source's own resume has that exposure with no overlap at all; harper-pro#922's closed floor replaces both.
    - **A fresh base copy** also resumes every relayed log in append order past its own last committed key (`collectRelayedLogAnchors` into `boundaryRange.startByLog`), with no time assumption. A relayed log whose boundary fails loses only its own anchor (`anchorsWithoutFailedLogs`) and starts from 0, as before this change; a corrupt frame or a probe that throws names no log, so every relayed log does. Only the anchors the tail resumes past ride `COPY_START[3]`, and those logs drop their key floor in the predicate. The receiver records them as its cursors once the copy finishes (only for origins it already has an id for), so a cloned node's first restart does not pull those logs from 0. A resumed copy gets none.
    - **Cursors are not bound to table scope**, like the direct `seqId` before them. If a subscription widens (a table turns on `replicate`, or a `receivesFrom` or the sender's `sendsTo` exclusion is removed) and the node resumes without a base copy, a relayed origin's rows in the newly included table keyed below its floor are not resent, just as the direct peer's own rows below `seqId` never were. Complete coverage after a widening needs a base copy (accepted on #989).
    - **Idle-peer resume** is closed by the origin-closed floor certificates of item 27 between peers that both certify; between others, a cursor past `auditRetention` forces a bounded base copy, as before: an idle sender whose retained last local key is older than that cutoff can copy again on every reconnect, and an empty local log uses the copy's wall-clock anchor and reaches the cutoff again after a retention window.
    - Nothing here deletes or purges a log, an entry or a `seq` row: a removed member's earlier writes stay valid.

27. **Origin-closed floor certificates (harper-pro#922 item 2; the producer is core's "Origin-closed timestamp floor").** A position — the sender's scan position in the `end_txn` trailer, a frame's key, a skipped-record `SEQUENCE_ID_UPDATE` — is never proof that resume may start there: a log is appended in commit order, not key order, so a transaction reserved below the position can still commit. Core certifies a floor `F` for its own `local` log below which nothing can append; this carries it to peers so an idle origin's receivers keep a proven resume point instead of ageing past retention (#989 defect B).
    - **Wire.** `[SEQUENCE_ID_UPDATE, position, { originName: floor }]`, the existing standalone position update with an optional third element, sent only to a peer whose bag resolves `originFloors ≥ 1`; a peer without it is byte-for-byte on the old protocol. Pings stay transport liveness.
    - **Sender** (`replicateOverWS`'s subscription loop). At the top of a pass, at most every `ORIGIN_FLOOR_INTERVAL_MS` (30 s; `HARPER_TEST_ORIGIN_FLOOR_INTERVAL_MS` for tests), `captureOriginFloors` reads this node's floor as a number (`readOriginClosedFloor`, 0 = none) and, for a multi-log range, `collectRelayableFloors` for every unlisted, unexcluded origin. After the pass drains it sends the floors that rose since the last emission to this peer (`certifyOriginFloors`), after the `end_txn` trailer. **Capture before scan is the ordering proof:** every entry below a captured floor was in this node's log before the capture — its own log by closure, a relayed log because this node persisted that floor only after applying them — so the drained pass has sent every one of them in the peer's scope. A pass whose range reports `exactStartFailures`, `failedLogs` or `corruptFrameStop` certifies nothing on that range again. The idle wait gains a timer of the same interval so an idle connection reaches the emission point; the `whenNextTransaction` reaction is registered once per transaction generation (a timed wake sees the same pending promise), and a commit that landed during the scan is detected by the promise having rotated.
    - **Receiver.** `receivedOriginFloors` validates each floor with core's `isValidFloor`, resolves names through the durable id mapping without minting an id, drops this node's own name and anything during a copy, and records `relayable = exclusionOrigins.includes(origin)` — this node receives the origin directly with full table coverage (`computeExclusionOrigins`), so it holds everything the origin certified. The floors ride that update's own `seqUpdateEndTxn` event and become eligible only in **its** `onCommit`, which core awaits after every apply queued ahead of it; under the durable watermark's blob rule (`cursorBlockedByBlob`) they wait in `PendingOriginFloors`, released by the next sequence update, frame commit or the blob-drain re-emit. Core merges `originFloors: [nodeId, closedFloor, relayable][]` into `nodes[].closedFloor` by max (core `resources/DESIGN.md`), apart from `originLogKey`. An unrecoverable source blob (harper-pro#403) leaves `hasBlobGap` unset and so does not hold a floor, the rule the cursor already follows.
    - **Resume.** `SUBSCRIPTION_REQUEST` uses a stored floor where it is newer than the position, and only while the peer still advertises the capability (a downgraded peer may write below a floor it saved): the direct peer's `startTime = max(seqId, below(F))` (`resumeStartWithFloor`), and the per-origin vector value `max(originLogKey, below(F))` (`buildOriginCursorVector` with `useFloors`), where `below(F)` (`cursorBelowFloor`) is the float64 under `F` because the direct start is exclusive and `F` can equal the key of a transaction still open. The sender's resume code and `shouldForceBaseCopyForRetention` are unchanged: the request now carries a fresh start, so an idle sender older than the cutoff and an empty local log both resume incrementally. A busy origin's resume keeps the position's late-commit exposure; exact floor-only resume is #922 item 4.
    - **Relay.** B forwards A's floor to C from B's own direct row for A, and only when that row marks it relayable, behind B's drained scan of A's log: the floor C stores for A is the one A certified, and B held every table of A when it certified. A floor received over a relay is never forwarded, so propagation is one hop beyond a direct full-coverage link; a fourth node reached only through C stays data-driven for A, as before. B mints nothing from its own receipt time. An older or LMDB relay stores no floor and forwards none.
    - **Not covered.** Cursors and floors stay unbound to table scope (item 26); item 1's power-loss residual (an advertised floor is WAL-durable, not fsynced) is inherited; a floor is the same trusted-peer assertion as the position trailer, not an authenticated proof. Regression coverage: `unitTests/replication/originFloors.test.mjs`, `protocolCapabilities.test.mjs`, core `replicationSeqCursor.test.js`, and `integrationTests/cluster/idleOriginFloorResume.test.mjs`.

**A receiver's rows on screen do not prove its resume cursor is on disk.** Core commits a batch's rows, then its `onCommit`, then the `[seq]` cursor (`core/resources/Table.ts` `updateRecordedSequenceId`), and a base copy's cursor also waits on a memtable flush (harper-pro#480). A test that stops a receiver soon after its rows appear can restart it cursorless, and it then full-copies the source's tables instead of replaying the source's log.
